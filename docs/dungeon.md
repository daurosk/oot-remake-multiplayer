# Dungeons the same for every player

Status: the tables are read from the game's files; the sharing is tested on fake games (`tests/lichii/dungeon_test.cpp`); none of it is played through in a dungeon yet (issue 87).

Plan stage 5: "if someone triggers something in the Water Temple, all players see it happen". Switches, doors, torches, room clears and water levels. Breakables and movable blocks are [world sync](objects.md)'s; enemies are [objects.md](objects.md).

Game: main of build e0f3ccfaf50065ae (1.1.1), romfs of the same version. **Checked** means read from the game's files. **Live** means seen in the running game.

## What is shared, kind by kind

Every kind of dungeon state, where the game keeps it and whether co-op shares it. "Named" = a named Bool or Int flag of the list above; "key" = a 64-bit placement key ([flags.md](flags.md)); "item" = [items.md](items.md).

| Dungeon state | Where the game keeps it | Shared | How |
|---|---|---|---|
| Switches pressed (floor, eye, crystal), shutters and barred doors opened | Named, written by the room logic (`…_Switch_…`, `…_OpenDoor…`, `…_ShutterOpen`) | Yes | Live, last write wins (host's answer) |
| Torches lit for good (puzzles that stay solved) | Named (`DodongoCavern_CandleStick`, …); the Well's `Obj_Well_CandleStick_A_03` is a key | Yes | Named live; key as one-time |
| Torches that burn out, timed switches | In the actor, or flags of reset type 280 | No | Room-local, back on a reload; each player solves their own |
| Order puzzles (the Scrub Brothers 2-3-1) | The order in the manager actor's own code; the solve in named flags | **The hits, new**, and the solve | A brother hit in one game is given to every other game's manager the game's own way, so players can split the order (below) |
| Room cleared (its enemies beaten, the shutters open) | Named `…_Clear`/`…_Cleared`, and the rooms' `Obj_EnemyCounter_*` keys (51) | Yes | Named live; keys one-time |
| Enemies, pots, grass, ice pillars | Keys of reset type 88 or 280: back on a scene load | No | [objects.md](objects.md) syncs the ones on screen |
| Mini-bosses and bosses beaten | Named (`…_Boss_Defeat`, `…_BossBattleEnd`…) and the heart container's key | Yes | Named live; key one-time |
| Chests opened (small key, map, compass, boss key, items) | Key of the chest's placement, reset type 24 (140 dungeon chests) | **Yes, new** | One-time key: opened in one game, opened in all; never closes again |
| Silver rupees and their counters | Keys (`Obj_RupeeToken_Silver` 85, `Obj_silverRupeeCounter_*` 17) | **Yes, new** | One-time keys |
| Walls and floors blown or hammered open, webs burnt, red ice melted, ghost paintings, skull pots, falling floors | Keys of reset type 24 (`WallCrack`, `*_CrackWall_*`, `*_SpiderWeb_*`, `Obj_RedIce_*`, `Obj_FireTemple_HammerSlipPillar_*` …) | **Yes, new** | One-time keys |
| Gold Skulltulas in dungeons, heart containers, the few hearts and rupees of type 24 | Keys | **Yes** (also as pickups, [items.md](items.md)) | One-time keys |
| Water level (Water Temple) and other dungeon Ints | Named Int (`WaterTemple_Room00_WaterLevel`) | Yes | Live, last write wins |
| Map, compass, boss key owned | Item: `DungeonInfo.<dungeon>.IsGetMap` / `IsGetCompass` / `IsGetBossKey` | Yes | OR: once anyone has it, everyone has it |
| Small keys in the pocket | Item: `DungeonInfo.<dungeon>.SmallKeyNum` (Int) | Yes | **One shared count per dungeon** (below) |
| Locked doors unlocked | Named (`…_UnLock`, `…_OpenDoor…`) | Yes | Live |
| Business scrubs sold out, fairy fountains (reset type 25) | Keys | No | Not known what type 25 means; left out |
| Where each player is, Navi's hints, the camera, "in battle" | Named, reset types 1, 9, 32, 40, or one-player names | No | Each player's own |

### Small keys: one shared count

`SmallKeyNum` is a count, not a flag, and uses the count (delta) rule of [items.md](items.md): every change a player makes (+1 for a key picked up, −1 for a door opened) is added to the one count all players have for that dungeon. So the players share one key ring. A key cannot be had twice: its chest is a one-time key (above), so once one player has opened it, it is open in every game and the +1 is counted once. Keys that drop from an event write named flags that are shared (`FireTemple_GetSmallKey_01` to `_08`, `BottomOfTheWell_Level_Room_03_Get_SmallKey`). The only two loose `Obj_Dungeon_SmallKey` placements (Bottom of the Well and Shadow Temple, `*_Static`) have no key of their own; the Well's has the named flag just given, the Shadow Temple's is not mapped and could be taken twice (check in a run). A door opened by one player costs one key for everyone, and the door's flag opens it in the other games, so nobody pays for it twice.

### Later players

A player who joins later gets the host's table of every shared flag and key (`FLAG_SNAPSHOT`, [protocol.md](protocol.md)): doors open, chests open, rooms cleared, keys and dungeon items as the group has them. One exception from the one-time rule: a key a late joiner's own save has at 1 while the host's is 0 stays 1 in the joiner's game but is not sent to the host (the watcher's first read is its baseline); it reaches the others only when it changes again.

## The placement keys

`CoopDungeon::Keys()` (`lichii/hook/coop_dungeon.cpp`) lists the 500 placements in the 13 dungeons' Banc files (`Banc/<Dungeon>/*_Static.bcett.byml`, `*_Dynamic.bcett.byml`) whose `Hash` is in `GameDataList`'s `Bool64bitKey` table with `ResetTypeValue` 24 (checked; 522 had type 24 or 25, the 22 of type 25 are left out). Every chest in a dungeon has such a key (checked: no `Obj_TBox_*` in a dungeon lacks one). They join the shared list in `Merge`, so they are shared even with `LICHII_COOP_PICKUPS=0`; with pickups on (the default) the hook also hands each to `Session::share_pickup`, which makes them one-time: a 1 goes to everyone, and a 0 (the game's own table being reloaded, or a 0 from another game) is never sent and never written over a 1.

## How it is shared

`CoopDungeon::AddShared` adds the 1,009 flags (776 from the scan, 190 played gimmick events, 43 the softlock audit found) and the 500 placement keys to the session's shared list (`docs/flags.md`), next to the items and the user's flags file, unless `LICHII_COOP_DUNGEON=0`. The flag watcher then carries every change live: the player who pressed the switch writes the flag in their game, the host's answer sets it in every game, and the other games' room logic reads it like its own.

### Held until the room loads (issue 129, player report)

A player test: in the Deku Tree slingshot room A shot the eye switch and A's ladder fell. B's ladder did not fall, B's eye stayed open, and shooting B's own eye then did nothing: a softlock. B's ladder was down after B reloaded the save. So the shared flags were right, but B's loaded room did not play the result, and the played-event flag stopped B's own switch from playing it. The game has no known way, from the hook, to start that event in B, and the scene change that would reload the room is taken only while an event runs. So the rule is the other half: **never mark a gimmick done in a game without its result**.

- Every `HavePlayedEvent.<gimmick>` flag of the list (194) and the Forest Temple corridor's state flags (`ForestTemple_TwistCorridor_IsReverse`, `…01/02_IsConstraint`, `ForestTemple_SageOfForest_TwistedCorridor_A_01` to `_04`) are held while our Link is in that flag's dungeon (`CoopDungeon::HeldIn`; a gimmick event of no one dungeon is held in any dungeon).
- Held means our game does not take it yet (`coop::host::HoldFlagStore`). The watcher keeps the value and writes it as soon as our Link is out of that dungeon, or the game is loading (no Link: a save load, a scene change), so the room loads with it. A host answers a held write with the value asked, so the group keeps it.
- Meanwhile our own switch still works: shooting B's eye plays B's own ladder event. Its flag then goes out as B's change, and the held value is dropped (the game set it itself).
- The room's own flags (`…_RoomC_Cleared`, switches, doors, the water level Int, small keys) stay live. The pillar in the slingshot room followed them live in the 2026-11-10 player test.
- The log says `coop: dungeon: room gimmick flags from another player held until we leave this dungeon or load` and `no room gimmick flags held`.
- The corridor (docs/sync-coverage.md): its state is shared, but never applied under a player who is in the Forest Temple; it is applied on their next load or entry.
- **Not held** (player test): the Deku Tree basement water (`…_Gimmick_RoomG_WaterLevelDrop`) and the torch room (`…_Gimmick_RoomH_CandleStick`) already came live in the other game through their room flags, so their played events stay live too.
- **A load never undoes a held value for the group.** A held flag written while there was no Link (the join snapshot, a save load), which the save then loads over with 0 while our Link is in the dungeon, is kept to write later. Its 0 is ours alone and is never sent (review of 08fad87).
- **Released only after a real load**: about 0.5 s (30 frames) without our Link, not one frame the reader missed. The scene is the last one read.
- **The way out** when a gimmick's own trigger is itself a live-shared saved flag (B's switch already counts as pressed, so B cannot play the event): leave the dungeon (or reload) and come back. The room then loads with the event played. The live events (below) start the event in B's game instead, once B's Link comes near it.
- The live room flags of reset types 9 and 40 are one way (above), not held.

### Live events (issue 129; on by default since dungeon-switches, off with `LICHII_COOP_LIVE_EVENTS=0`; not yet run in a game)

The hold above is the safe floor. The goal is the result live: the ladder falls in B too. Read from `main` (via the static recompile in `dump/generated/main` and the strings of the plain image):

- The AI node `SeqOneShotRequestEvent` (name getter 0x32db330, execute **0x32db1a0**) starts an event by name. It builds a 0x1b20-byte request (`0xd79f10(arg)`), copies its input string into the request's own 0x80-byte name buffer (pointer at +0x1a90, capacity at +0x1a98), and calls **`0xd7a820(manager, arg)`** with `manager = [[main + 0x4c7e090]]`, the same event manager the force skip uses. Then it puts the base vtable (main + 0x4974b20) on the two string members at +0x1968 and +0x1950 and frees each with `0x20b6f0`. Related nodes, not used: `OneShotEventMemberRequestEventByEventName`, `OneShotEventPerformerRequestEventByEventName`, `ExecuteQuadrupedRequestEvent`.
- A held gimmick event (above) is started in our game the same way, from the svc cave on the calc thread (`coop_live_events.{h,cpp}`; the cave is there when puppets are on, as in every kit). The request block comes from the game's `malloc` once. If it plays, the game sets its played flag itself and the held value is dropped. If it does not (a wrong name, for example), the hold stays, as before.
- **When** (dungeon-switches, issue 176): each event only while our Link is within 18 m (`CoopLiveEvents::kNearM`) of a placement that asks for it, so its room is loaded and the player sees it; once per visit of the scene; never while an event runs. Away from it, the event waits (held) until our Link comes near. The places (`coop_live_places.cpp`, 204 places for 198 events) are every placement in the 13 dungeons' Banc files whose `RequestEventName`, `ShutterEvent`, `NomralEvent` or `OpenChainShutterEvent` names a shared gimmick event, at its `Translate`. 5 shared events have no placement (story scenes, `WaterTemple_WaterLevelChange01`, asked by graphs): never started here. 18 m: the slingshot room's door and chest ledge are 11 and 17 m from the ladder's asker, the compass room's asker 20 m from that door.
- `LICHII_COOP_LIVE_EVENT_NAMES=a,b` limits it to those events (a named event with no place starts anywhere in its dungeon); `all` or unset: every event with a place.
- The Deku Tree switches of the 2026-11-11 player test (issue 176) are all such events: the slingshot room's eye (`InsideTheDekuTree_Gimmick_FallingLadder`, asker at -37.5 117.8 12.5), the compass room's plate (`Obj_StepSwitch_A_02`, timed 20.2 s; `…_Gimmick_RoomD_PlatformUp`, -22.6 122.6 -3.8), the plate and torch that burn a web (`Obj_StepSwitch_A_05`, `Obj_SwitchCandleStick_A_02`; `…_Gimmick_CandleAndSpiderWeb`, -10.0 82.5 -9.5), the second eye (`…_Gimmick_RoomF_EyeSwitch`, -14.5 82.7 27.8). Before, they were held (the result only after a reload), as above.
- Logs: `coop: dungeon: starting the event <name> here (another player played it)`, `coop: dungeon: live event <name> asked of the game (result N)`. An event asked once is not asked again in the same visit, even if the request did nothing: leave the dungeon and come back to retry.
- Not known until a run: whether a placement's `RequestEventName` (the name the played flag is made from) is the name this request wants, and whether a request made while the room's own logic does not expect it plays the ladder. The run answers both (the `deku-ladder` scenario and the in-game checks in `reports/dungeon-switches.md`). If an event crashes or misplays, `LICHII_COOP_LIVE_EVENT_NAMES` narrows the list, or `LICHII_COOP_LIVE_EVENTS=0` turns it off.

### The slingshot room's bridge and the webs (dungeon-switches, issue 177)

Issue 177 (player test 2026-11-11): the bridge and the webs vanished in the other game instead of falling or burning.
- **The bridge** is the three falling floors `Obj_InsideTheDekuTree_FallingFloor_A_01`, `_A_02`, `_A_03` (-39.8 to -44.8, 109.8, 11). `_A_01`/`_A_02` have a saved key, so the other game removed them at once when the key came. They have their own fall AI (`ActorLogicFallFloor`, a fracture) and no life, so no life write plays it. Now all three are shifters ([world.md](world.md)): the fall in the game that did it is sent as `WORLD_MOVE`/`WORLD_PLACE`, and the key's removal waits 4 s (`kTakeFallUs`, `CoopWorld::IsFallTaken`) so the fall shows first. The Shadow Temple's keyed floor stays as it was (kept as ground).
- **Shifters are sent from across the room.** A shifter moves only by its own AI when hit in that game, so the game where it moved sends it from up to 40 m (`kShifterReachM`), not 15 m: the eye is shot from the chest ledge, 17 m from the ladder, and the ladder fell only for the shooter.
- **Webs**: a web with a life gets life 0 and plays its own break (breakables-2). The web's visible parts (`*InteractiveSpiderWebParts_*`, keyed, an AI of their own, no life) were removed at once; they now wait 4 s too, so their own reaction to the web's break can show. A web with no life (the floor webs you fall through, `SpiderWeb_A_01`) still goes at once: nothing to play.

**The gimmick probe** (`CoopWorld::GimmickProbe`, `lichii/hook/coop_world.{h,cpp}`; off unless `LICHII_COOP_GIMMICK_PROBE=1`, since it reads about 25,000 words every 0.5 s; the integrator turns it on for the run; reads only). Every 0.5 s it copies the 4 nearest gimmicks within 15 m of our Link: `*StepSwitch_*`, `*EyeSwitch_*`, `*SwitchHit_*`, `*SolarSwitch_*`, `*SwitchCandleStick_*`, `*WaterPlane*`, `*SwitchShutter_*`, `*CandleStick_*`, `*ElevatorLift*`, `*MoveFloor_*`. Each copy is the actor, its component table and 0x200 bytes of each component, as the sign probe reads a sign. It logs each word that stepped (equal in the two copies before, different now): `coop: gimmick probe: <hash> <name> <d> m from our Link: N words stepped: actor+0x..:<before>><after> c+0x..+0x..:...`. A word that steps more than 6 times (a timer, a counter, a moving part) is muted. `gimmick probe: watching <hash> <name>` marks each one it starts to copy. In the run, pressing a switch in A shows its words in A's log; B's log shows whether B's copy of that switch changed with it.

## Locked doors (branch `locked-doors`)

A small-key door is a door set (`Logic/Module/DungeonDoorSingleWithChainLockSet`, `DungeonSwitchShutter…WithChainLockSet`, placed as `AiGroups`) with a lock actor, `Obj_DoorChainLock_*` (98 placements: Fire 16, Gerudo Training Ground 18, Forest 11, Shadow 10, Spirit 10, Water 9, Well 4, Gerudo Fortress cells 4, Ganon's Castle 3, the rest in the Dream World). The lock's AI (`AI/DoorChainLock.root.ainb`) spends the key (`OneShotDungeonUseSmallKey`), saves "open" in a bool it makes from its placement (`QueryGetIsGenerateAutogenGameDataFromGameBancParam`, `OneShotSetGameDataBool`) and deletes itself (`OneShotDeathRequestDeath`). That bool is no placement key and no name we could hash, so it is not in the shared list; only some rooms also write a named flag (Forest `…_LockOpne`, Spirit `…_Unlocked*`, Ice Cavern, the Well).

With the key count shared and the lock not, the second player found the door still locked with the key already spent for both: one key short per door, a softlock in every dungeon with locked doors. Now the lock itself is shared, as a world object (`CoopWorld::WorldSync`, [world.md](world.md)):

- **Opened here:** our lock leaves the actor list next to our Link (the game deleted it) and goes out as `WORLD_BREAK` with the `kept` bit (protocol 7).
- **The server keeps it** for the session, also while nobody is in the dungeon, and gives it to everyone who enters, a late joiner too. Other breaks are forgotten when a scene empties, since the game puts pots back on a reload; the opener's game never puts a lock back.
- **Opened elsewhere:** our copy of that lock is deleted (0.4 s after the break, or at once when its room loads later), so our door is open and no key of ours is spent. A lock deleted that way that comes back when its room loads again is deleted again, never reported as put back.
- **Never from under our Link:** while our Link is within 2.5 m of the lock, it is left alone (our player may be opening it). If it then leaves the walk next to our Link, that is decided like any break: after 0.7 s, and not when the area unloaded with it (four or more things gone at once, one far). If our player opened it, the key they spent was a second key for one door: the hook gives it back (adds 1 to `DungeonInfo.<dungeon>.SmallKeyNum` in our game; the flag watcher sends that +1 like any change, so the group's count is right). If they walk away instead, it is deleted.
- **Both at once:** two games that each opened the lock before hearing of the other both sent a break; the server passes the second one on too, and the game with the higher player number gives its key back. So the group spends exactly one key per door.
- **Only against a key we spent:** a key goes back only against a drop of our own game's count of that dungeon in the last 8 s (`FlagWatcher::take_own_count_drops`: what our game did, never a total the watcher wrote in for another player), and each drop pays for one give-back. So a lock that left with a warp, a death or a room unload, or a door set's second lock, or a boss lock (no small key), gives nothing (`…, but no key of ours went: none back`). A lock opened in a scene with no small key count logs `opened in a scene with no small key count` once.
- **A host save load** (branch `host-save`, `FLAG_RESET`) puts the keys back as the save has them, so the kept breaks must go too: the server's `WorldStore::forget_kept()` and the games' `CoopObjects::ForgetKeptBreaks()` (`WorldSync::ForgetKept`). Both are built and tested here; the integrator calls them where `FLAG_RESET` is taken (the server's host `FLAG_RESET` handler; the hook's `flag_reset` event).
- Log lines: `world: <hash> Obj_DoorChainLock_A_01 broken here (gone next to Link): sent`, `… broken by another player (no life: deleted after a wait)`, `… was broken before we saw it: deleted`, `world: <hash> lock opened here after another player: one key back`, `… opened by both at once: one key back`, and from the hook `coop: doors: small key 0x… given back (N -> N+1)`.
- Not the Market shops' night locks (`Obj_HrlCity_Shop_DoorChainLock_A_01`), and no `Dm_` copy.

Not known without a run: whether the door opens when its lock is deleted by our call (the door set's logic reads the lock's link; a lock gone may count as open, or the door may stay shut). If it stays shut, the next step is to find the lock's bool in a run (`LICHII_COOP_DEBUG_FLAGS=1` while opening one) and share that instead. Also not known: a session that ends and starts again forgets the kept breaks; a player whose own save has the door locked then pays for it again (their key count is the host's).
