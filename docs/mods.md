# Mods

Co-op on Longshot has its own mod loader. It sits in the pause menu's **Mods** tab, right after **Multiplayer**. It loads two kinds of mods from the game's own `mods` folder:

- **Game file mods** (RomFS: textures, models, text, a randomizer seed). The game reads them when it starts.
- **Code mods**: a library (`.dll`) that the co-op module loads when the game starts. It can read and write the game's memory, run something every frame, draw over the picture, take keys and hook game functions.

The randomizer (OOTRR) is built in.

## For players

### Where mods go

Put each mod in its own folder under `mods` beside `longshot.exe` (in the kit: `hookshot\game\bin\mods`; or the folder `HOS_MODS` names):

```
mods\
  better-hud\romfs\...            a game file mod (as made for emulators: works as it is)
  camera-tweaks\mod.json          a code mod: its mod.json and its .dll
  camera-tweaks\camera.dll
  oot-remake-randomizer\mod.json  the randomizer's switch and settings (made by the game)
  randomizer-AB12CD34\romfs\...   a seed the randomizer built
```

A mod made for an emulator's `load\<title id>\<name>\romfs` folder works the same: copy the `<name>` folder into `mods`.

**Mods with code patches** (an `exefs` folder of `.ips` or `.pchtxt` files, for example [OoT Character Select](https://github.com/snaildev99/OoT-Character-Select)) work too: the game is compiled ahead of time, so the kit builds the patches into it (our patches 0034 and 0035; Longshot's own #134, after v3.0.0). Put the mod into `mods` and start the game as usual: the start sees the new code patch and builds the game again with it ("A mod's code patches changed": about 5 to 25 minutes, the PC stays usable). Each build is kept (the newest 3, about 650 MB each, in `hookshot\game-variants`; `data/game-variants` on Linux), so switching such a mod back on the Mods tab puts the build made before back in seconds instead of building again. The same happens when such a mod's patch changes, when it is taken out, or when it is switched off or moved on the Mods tab (the tab's order decides which patch wins a byte two patches write; switching or moving a mod without code patches builds nothing again). A patch for another game version (its file name is not the game's build id) is left out. `exefs_patches.txt` in the game folder lists the patch files the game was built with, and `hookshot_log.txt` names each mod's exefs folder at the start. A mod without code patches, and a game without such mods, build and play exactly as before.

### The Mods tab

- Each mod is a row: its name, version and author, whether it is on, and a note when something is wrong.
- **On / off** and **up / down**. The first row wins a file two mods have.
- **Settings**: a mod's own page (toggles, choices, numbers, text). A **text** setting: Enter types into it (Ctrl+V or Shift+Insert pastes the clipboard after what is typed; Enter keeps it, Esc leaves the old value). Without typing, **Left / Right** on the row (or a click on its sides) is **Paste**: the value becomes the whole clipboard, which is how a pad player sets a long string. Every text setting of every mod works this way and keeps its `max_length` (a longer paste is refused with a line saying so, never cut). A value longer than the row shows its start and end; while typing the row shows the end and a line under it counts the characters.
- **The randomizer's row** reads **OoT Remake Randomizer** with a **Settings** button and no Off / On: press it to open its page, where the **Randomizer** switch, its seed, its settings and its status line are.
- **Restart needed**: game files and code are read only when the game starts. The tab says what changes at the next start; nothing is ever rebuilt.

The tab writes two files into the mods folder: `coop-mods.list` (order and switches) and `coop-mods.settings.json` (settings). The game reads the list at its start (our patch 0011). A game built without that patch loads every mod in its own order, and the tab cannot switch or move game file mods (code mods and settings still work).

### A mod that fails

A mod whose `mod.json` is broken, whose library does not load, that says no at its start, or that crashes, is switched off for this run with one line in `hookshot_log.txt` (`coop: mod <id>: ...`) and a note in the tab. The game and the other mods go on. `HOS_COOP_MODS_CODE=0` loads no code mod at all.

A mod whose code crashes the whole game or hangs it while it starts (a crash the guard cannot catch: a stack overflow, a fast fail, its own thread) is skipped at the next start and switched off, with a line in the log and a note in the tab; switch it on to try again (the game writes `mods\coop-mods.starting` while each mod starts). After the guard catches a crash the game goes on without that mod, but the mod may have left the game odd until the next start.

### Mods in co-op

Every game tells the others which mods it runs (ids, versions and a hash of their files). When yours differ from the host's, the chat says so once and the Mods tab lists what differs: a mod you miss, one the host does not have, another version, or other files. The host is told which player differs. You can still play: a mod that changes what is in the world (items, chests, enemies) may then make your games disagree.

A mod marked `"coop": "own"` (a HUD, a camera) is your own business and is not compared.

A setting marked `"shared"` is the host's in a co-op game: your tab shows the host's value, locked. The randomizer's seed is one. A guest keeps the host's values as its own afterwards, so a restart before joining again plays the same seed; change them in the tab to play your own.

### Character Select

[OoT Character Select](https://github.com/snaildev99/OoT-Character-Select) by snaildev99 (Snail) lets you play as the game's other characters (Saria, Sheik, Darunia and over a hundred more), and the other players see your pick on your puppet (docs/puppet.md). It is Snail's mod and he distributes it: the kit carries none of its files (its release holds the game's characters rebuilt from the game's own files; The Legend of Zelda: Ocarina of Time and its characters belong to Nintendo; the mod's code is MIT).

- **The Characters page comes with every kit (0.11.9).** His page in the − menu, his Customize screen (filled by co-op's own Customize), Link's own models and his code patch go in for everyone. His NPC characters (their models, textures, cloth, voices and his Dark Link) are an opt-in download.
- **Asked once.** At the first start (Windows `Start Squadala.bat`, Linux `start-squadala.sh`) the kit asks `Download the NPC characters for the Characters page? [y/N]` with a 15-second countdown: Y is yes; Enter, N or no key is no. A start with no console or terminal takes no. The answer is kept (`hookshot\character-select-answer.txt`, Linux `data/character-select-answer.txt`; Update.bat keeps it).
- **Change it later** at any start: the kit shows `Characters page, NPC characters: on|off` and N within 2 seconds switches it (no file to edit). `character_select = yes|no|ask` in `coop-options.ini` does the same and wins over N. Taking them out is done from the copy there (no download); getting them later downloads the release again.
- **His customizer is left out.** Co-op's Customize is the one customizer, so the kit drops exactly the records of his customizer from his code patch (the two places that call it, `cz_head` and `cz_frame`, and the routine and table bodies his MIT source `mods/customize.py` names). Every other record (the picker, the model, cloth and voice hooks) is kept byte for byte; his patch as he made it stays beside the folder's files as `coop-charsel-code.ips`, outside `exefs`. A release laid out otherwise is refused and the copy there kept.
- **A character that is not downloaded.** His full picker stays. Picking a character whose model is not installed (or loading a save stored with one) puts the pick back at once (the last downloaded one, or Link) and the chat says `This character is not downloaded: press N at the kit's start to get Snail's NPC characters.` Another player's pick you do not have shows as Link, and the chat says so once for that player.
- **What the download does.** The kit downloads Snail's release named in `hookshot\CHARACTER-SELECT.txt` (v0.2.2, a 145 MB zip) from his GitHub release page and his `characters.json` (the list of characters the puppet pack reads) from his fork at a fixed commit, checks each file's SHA-256, and puts the mod's one folder into the game's `mods` folder as `OoT Character Select`, with `characters.json`, `CREDITS-coop.txt` and his `LICENSE.txt` beside its `romfs`. Since v0.2.2 the zip holds only his own files; its tool folder (`build-from-your-game`) then makes the models, textures, menu archives and tables from your own game's RomFS with the kit's Python (about 2 seconds for the default part, a few minutes and about 1.1 GB on disk with the NPC characters; the tool checks every source file and result, and a game of another version is refused file by file with the reason shown, nothing half-made is kept). The mod is put in only together with its files (never half-made, on both systems): on Linux the first start has no game RomFS yet (the game is built after that step), so the Characters page is put in at the second start, which then builds the game again with its code patch. The zip is deleted afterwards. A file with another SHA-256 is refused. Updating from v0.2.1 installs v0.2.2 fresh and keeps the old copy until the game is rebuilt, so the check wants about 3 GB free. When this PC is offline, has less than about 3 GB free, or a download fails, one line says so and the game starts without it; the next start tries again.
- **On, and the Mods tab switches it off.** The kit never writes the Mods tab's list, so your Off stays, also over updates. Its code patch (`exefs`) is built into the game by our patches 0034 and 0035, so putting it in, updating it, taking it out or switching it in the tab builds the game again (about 5 to 25 minutes; switching back to a mix built before takes seconds). The puppet pack is made again with its characters (1 to 4 minutes; the pack made before is kept, so switching back puts it back in seconds).
- **A copy of your own** (a `mods\OoT Character Select` folder you put in yourself) is used as it is and never replaced or removed by the kit.
- **On a first start** the game is built first (20 to 40 minutes), then the mod goes in and its code is built in (a few minutes more).
- Without it nothing changes: solo and co-op play as before, and other players' character picks show as colour puppets.

### The randomizer

The OoT Remake randomizer is [OOTRR](https://github.com/ootrando/ootrr) (by REALAZK, GPL-3.0-or-later since 0.5.0). The kit brings it: there is nothing to download or set.

- **OOTRR comes with the kit.** The kit's game build (`Start Squadala.bat`'s first build, or its "putting the updated co-op into the game" step) downloads the OOTRR release named in `hookshot\OOTRR.txt` (0.8.2 in 0.11.11, a full release; 0.8.1 in 0.11.9; 0.8.0 in 0.11.8; 0.11.5 to 0.11.7 had 0.7.3; 0.11.4 had 0.6.2, 0.11.3 had 0.6.1, 0.11.2 had 0.6.0), checks its SHA-256 and puts it in `tools\ootrr\` beside the game (`hookshot\game\tools\ootrr\ootrr.exe`, with its `LICENSE` and `NOTICE`). The Linux kit does the same into `data/game/tools/ootrr/`. When that download fails the build only warns, co-op plays without the randomizer, and the next start tries again.
- **Do not install OOTRR by hand next to co-op.** A second OOTRR (unpacked into `mods`, or set up as its own instructions say) crashes the game at start; the kit's own copy is all co-op needs.
- **A new OOTRR release makes the seeds again.** When the kit's build puts in another OOTRR release than the one the game had (0.5.0 to 0.6.0 in 0.11.2, 0.6.0 to 0.6.1 in 0.11.3, 0.6.1 to 0.6.2 in 0.11.4, 0.6.2 to 0.7.3 in 0.11.5, 0.7.3 to 0.8.0 in 0.11.8, 0.8.0 to 0.8.1 in 0.11.9, 0.8.1 to 0.8.2 in 0.11.11), it removes every built seed (`mods\randomizer-*` with its `coop-seed.txt`, and its seed file in `mods\oot-remake-randomizer`): the old release's seed files do not build with the new one, and the same seed word is another world with it. The game makes the seed again at its next start (about a minute, then a restart), so every player of the same kit plays the same world. A save of the old seed's world plays on, but the chests are the new seed's: start a new save. In co-op every player needs the same kit: a guest on an older kit (OOTRR 0.5.0 to 0.8.1) builds another world for the host's seed.
- **Settings OOTRR 0.8.2 builds:** default and keysanity. Its own easy, open_world and full_shuffle presets stop with "This build cannot apply these settings yet" (run with 0.8.1's `ootrr.exe generate`; 0.8.2's code for these checks is unchanged: easy asks for small keys removed and bridge from stones; open_world for an adult start and an open bridge; full_shuffle for shuffled scrubs and Ganon's Boss Key from medallions), so the Mods tab does not offer them (it tries each preset once per OOTRR, so a later OOTRR that builds them offers them with no change here). This is not new: no OOTRR since 0.5.0 builds them, and since 0.11.2 the Mods tab hides them instead of failing at the build; it is OOTRR's build that lacks those four settings, not a change of ours. What 0.8.1 and 0.8.2 build is the openness settings: Kokiri Forest open, Kakariko gate open, Zora's Fountain open, Door of Time open (`door_of_time_condition`), Gerudo Fortress open or fast, Ganon's trials skipped, boss keys and Ganon's Boss Key removed. The kit's own **Open areas** (forest, Kakariko, Door of Time, Zora and fortress open, trials skipped, boss keys removed) and **Open areas, fast fortress** (fortress fast, the rest open) choices in the Settings row are these settings as the strings below, so no pasting is needed; the Settings string row still takes any string. A string that builds, generated with 0.8.1's `ootrr.exe`: `OOTRR1-AMAQABABAADACAQHAEBA6AIACAAQCEQBAEPACAJGAEASOAIBGMAQCTABAFHACATJAEAG2AIDQ4AQCADGXY` (forest, Kakariko, Door of Time, Zora and fortress open, trials skipped, boss keys removed; small keys stay in their dungeons because they cannot be removed). Still refused by both: small keys removed, bridge open or from stones, adult start, shuffled scrubs. Kakariko open needs the forest open. A host's choice that a guest's OOTRR cannot build is said in the chat.
- **Spoiler log and settings string (0.11.4).** Every built seed folder (`mods\randomizer-*`) has OOTRR's spoiler log (`spoiler.txt`, from `generate --spoiler`; it spoils the item locations) and the seed's `OOTRR1-` settings string (`settings.txt`, from the seed file), for the players to share. Host and guests build the same seed, so their files are the same. The spoiler log is also kept beside the seed file (`mods\oot-remake-randomizer\<seed folder>.spoiler.txt`), and both stay when the kit builds the seed again. A seed built before 0.11.4 is made again once at the next start to write them (same seed, no restart). Steps: [randomizer.md](randomizer.md#sharing-the-seed-spoiler-log-and-settings-string).

- **A player on another kit.** The host's seed word reaches every player and each game builds it with its own OOTRR, so a player on an older or newer kit builds another world without an error. Since 0.11.2 the seed's files are compared (each player's mod list carries a hash of them): the host and the others get "Mods: player N (name) has the randomizer seed X built unlike the host's: on another kit (another OOTRR) it is another world (other items in chests); all need the same kit", and that player (on 0.11.2 or later) "Mods: your randomizer seed X is built unlike the host's ... update to the host's kit". Other mods on beside the seed change its size table, so they can show the same line; the Mods tab lists them.
- **Your game files are the kit's own.** The kit's build already unpacks your game beside the program (`hookshot\game\romfs`, or `data/game/romfs` on Linux). OOTRR reads them there and never changes them; nothing is copied. They are the game version co-op needs (program 0400486024DEC000, update v131072, which is the 1.1.1 OOTRR asks for), so they always pass OOTRR's version check.

1. In the Mods tab, press **Settings** on the **OoT Remake Randomizer** row and turn **Randomizer** on. With no **Seed** a new one is made. Pick **Settings** (default, keysanity, and the kit's own **Open areas** and **Open areas, fast fortress**; OOTRR's easy, open world and full shuffle presets are not offered because this OOTRR cannot build them).
2. The game builds the seed in the background (about a minute; OOTRR's output is in `mods\oot-remake-randomizer\last-build.txt`) into `mods\randomizer-<seed>` and switches it on, first row. An OOTRR that runs longer than 10 minutes, or while the game closes, is stopped; the seed is built again at the next start.
3. Start the game again, and start a new save.

Two rows are only for players who want something else: **Game folder** (other extracted game files, version 1.1.1, with `Pack`, `Banc`, `Event` and `System`; `OOT_ROMFS` does the same) and **OOTRR program** (another OOTRR). Leave them empty to use the kit's own. A row that names a folder or program that is not there says so; it does not fall back to the kit's.

When a seed cannot be built, the tab says why in plain words: OOTRR missing (close the game and run Update.bat, which sets it up again, or start the game with "Start Squadala.bat"; when the kit's last setup failed, the tab says why, for example an antivirus that took ootrr.exe: allow it in Windows Security > Protection history), the game files missing (build the kit's game again), or game files of another version ("not version 1.1.1": dump the game with update v131072 and build again).


In co-op the host's switch, seed and settings are everyone's: a guest's game builds the host's seed by itself, with its own kit's OOTRR and game files and nothing to set, and asks for a restart. A guest whose game still cannot build it (the download failed, for example) plays without the seed and sends one chat line, so the host's chat shows which player and why: "[randomizer] I play without the host's seed: <why>". The reason is a short fixed text ("OOTRR not found", "game files not found", "game files not version 1.1.1", "OOTRR could not build the seed (exit N)"), never a folder or a setting of that player: the full line with its paths stays in that player's own Mods tab and log. Their own chat says it loudly, with OOTRR's error line and what to do: "Randomizer: NO SEED - you play the BASE GAME, not the host's seed <seed> ..." (start the game again to try once more; if it still fails, ask the host for other Settings or send last-build.txt with a report). Whatever the cause, even a game without the randomizer at all, the host and every other player also get "Mods: player N runs WITHOUT the randomizer seed <seed>" from the mod lists, and "runs the host's randomizer seed now" once it does: that game is the base game, another world (other items in chests; bombs need the Goron Bracelet). Until that player builds it, their game differs from the host's (the Mods tab lists it). Every pickup is shared as without the randomizer. Each seed is built once and kept; switching back to a seed built before needs no build.

**Off by default.** The **Randomizer** switch starts off: a new kit, a new mods folder or a kit put over an older one builds no seed and plays none until you (or, in co-op, the host) turn it on. A seed folder our kit built (it has `coop-rando.txt`), left from an earlier kit, is switched off while the switch is off. A seed folder put in by hand (OOTRR's site or another tool: no `coop-rando.txt`) stays as the Mods tab has it; it is switched off only when you turn the switch off, when the switch's own seed plays instead, or as a guest (below; from 0.11.8 a guest keeps it when the host plays the same seed: "Sharing a seed you built yourself"). Before 0.11.5 every `randomizer-*` folder was switched off whenever the switch was off, so a hand-put seed played once and was silently off from the next start on (row 145). Turning it on or off says so in the tab and in the chat: "Randomizer on: keep the game open until this chat says the seed is ready, then restart it and start a new save" (or "Randomizer off: restart the game to play without it"); the same when the host's switch reaches a guest. When the seed is built (about a minute; a restart before that stops the build), the chat says "Randomizer seed <seed> is ready: RESTART the game now and start a NEW save (until then this game plays without it)", again when the game joins a host and every 3 minutes until the restart. A failed build is said in the chat too ("Randomizer: no seed, this game plays without it: ..."; a guest's also in the host's chat). The game never restarts by itself. A guest whose host plays without the randomizer (switched off, or a game without it) plays without it too; its own switch is kept for a game alone. The seeds a host's world switches off in a guest's game are listed in `oot-remake-randomizer\host-switched-off.txt` and switched on again when that game plays alone (with its own switch on, its own seed plays instead).

**Presets and logic.** All five presets keep OOTRR's default logic, "Glitchless": every item the seed needs can be reached without glitches, so the Bomb Bag comes before a wall that needs bombs, the Bow before the magic arrows, and progressive items (Hookshot then Longshot, bracelet then gauntlets, scales, wallets, magic) come in order. OOTRR's "No logic" and "Bombchus in logic (experimental)" are not in any preset and not offered here.

**Items in a randomized seed, in co-op.** An item from a randomized check is shared as any other ([items.md](items.md)), and comes with what makes it usable: a bag or quiver with its capacity and a fill, the Slingshot and Bow with their ammo, a bracelet or gauntlets with the lift grade (bomb flowers, bombs), an ocarina equipped and playable, and the magic meter (`Item_FairyBless_MP`, shared since branch `rando-items`) with a full meter, 240 a level as OOTRR gives it. A shared Silver or Golden Scale also raises `PlayerStatus.DiveDepth` (a Float) to 6.0 or 9.0, as OOTRR writes it, through the game's own Float setter. The Giant's Wallet (`Item_Wallet_Large`) gives room for 1000 rupees, as its own game data says. Magic Beans and Bombchus stay per player by choice: a shared bean or bombchu pack gives the others none ([items.md](items.md)).

Known limits: a seed is built with the other mods that are on at that time, the puppet pack (in `mods\contents\...\coop-puppet`) included: the game uses one resource size table, the seed's, so the seed keeps every other mod's larger entries (without the pack's, the game aborts while it loads). Turn other mods on or off before building, or build again. When the kit makes the puppet pack again (a kit update), its start builds every seed again (a few seconds each), or removes one it cannot build, which the game then builds at its next start. The game checks it too, at every start: a seed keeps the size tables it was built beside (`coop-tables.txt`, their paths, lengths and hashes); when they are not the ones there now (a pack made after the seed, by `make-puppet-pack` or a kit update; a seed from before this check), the seed is built again in the background and only its size table is taken (its items stay). When that table changed, the chat says "Randomizer seed <seed> was made again for the co-op puppets: RESTART the game to see the other players (your save stays)". Until that check is done, and for the rest of a run whose table was made again (the game read the old one at its start), no co-op puppet is made: a puppet made with too small a size entry crashed the game when the map loaded (lane1, 2026-11-15). The other players show as their fairies meanwhile, and the log says why. Before this, a pack made after the seed left the other players invisible with the randomizer on (the puppets' files had no sizes in the seed's table) while they were seen with it off. Starting items are OOTRR's (its starting module, on a new save, for each player who plays the seed): older OOTRR builds applied only the Kokiri Sword, Deku Shield and Slingshot; newer ones also give bags, strength, scales, magic, ocarinas and bottles (`start_items/give.rs`). Not checked with the OOTRR in the kit.

A seed made outside the Mods tab (OOTRR's own page, then its mod folder put into `mods` by hand) is not one of ours: its size table was made without the puppet pack's entries, and when that mod's table is the one the game reads (it is above the pack, as every listed mod is), the other players cannot be shown. At its start the game finds that mod (of the mods it loaded with `romfs\System\Resource\*.rsizetable.zs`, the one it indexed last, from `coop-mods.applied`: the list's first row wins; a mod the list does not name yet, one put in since the last start, sits at the pack's place and wins only when its folder name sorts after `contents\0400486024DEC000\coop-puppet`; when the winner is the pack or one of our seeds, nothing is held) and makes no co-op puppet for that run (the others show as their fairies, no crash). The chat names the mod: ""<name>" is a mod with its own size table (e.g. a randomizer seed from OOTRR's site): other players can't be shown. Make the seed in Mods > OoT Remake Randomizer > Settings, or turn this mod off.", again when joining, and the other players get "[randomizer] my mod "<name>" has its own size table (e.g. a seed from OOTRR's site): I can't see the others ...". The same goes for any other mod with its own size table above the pack. Not when the kit's start merged that table (the mod's entries and the pack's in one table, written into that mod): then it leaves `coop-merged.txt` beside the mod's `romfs` ("coop-merged 1", then "table <file> <hash>" and "pack <hash>", FNV-1a 64 of the two tables' bytes in 16 lower-case hex digits), and while both tables are still those bytes the game makes the puppets and says nothing. A new table dropped in, or a rebuilt pack, makes the mark stale: held and said as above until the next kit start merges again. Such a seed is not built in the guests' games: a guest gets only the Mods tab's seed and preset, or plays the same hand-put seed when it has the same folder (below). So in co-op the Mods tab is the easy way, where the host's seed reaches every player.

**Sharing a seed you built yourself (from 0.11.8).** A seed made outside the kit (an OOTRR built from source, newer than the kit's, or OOTRR's own page) plays in co-op when every player has the same folder:

1. Make the seed and build it for Hookshot (`ootrr build <seed file> <game> <mods> randomizer-<seed> --host hookshot`): a folder named `randomizer-<seed>`.
2. Send that whole folder to every player (zip it). Each player puts it into their own `mods` folder, the same name, as it is.
3. The host leaves the **Randomizer** switch off and hosts. Start each game from the kit, so its start merges the co-op puppets' entries into the seed's size table.
4. Guests join as usual and start a new save.

The host's game tells the guests which seed folder it plays and a hash of its files: every file under the folder's `romfs`, by path and bytes. The two files the kit's start rewrites in it (the size table and the actor tables, for the co-op puppets) are read from the copies the kit keeps of the seed's own (`_coop-size-table`, `_coop-rows`), so two players' copies match after each one's merge; nothing outside `romfs` counts. A guest whose folder of that name has the same files keeps it on (switched on, and to the first row, when it was off in its Mods list; then a restart; listed in `oot-remake-randomizer\host-switched-on.txt` and switched off again when that game plays alone) and plays the host's world; its other seed folders are switched off for the host's world and back on when it plays alone, as before. A guest without that folder, or with other files in it, plays as before: every seed folder switched off for the host's world (the base game's chests), back on alone. The chat says which: "Randomizer: the host plays the seed randomizer-X, and yours is the same: it stays on", "..., which you don't have: you play the base game's chests. To play it, copy the host's randomizer-X folder into your mods, then restart" or "..., and yours is not the same as the host's: it is switched off for this world (the base game's chests). To play it, delete your randomizer-X folder, copy the host's in, then restart" (a copy over the old folder keeps files only the old one had, so it would still not be the same), and the host's chat gets "[randomizer] I play without your seed randomizer-X: I don't have it" (or "mine is not the same as yours"). The Mods tab's seed still wins: a host with the switch on and its seed built plays and sends that one, and a guest switches every hand-put seed off for it. A guest joining mid-game gets the host's values from the server like any other. Only a folder named `randomizer-*` is checked this way; a seed folder of another name is a mod like any other (co-op never switches it, so each player plays the one it has). Since 0.11.8 the kit's start leaves a hand-put seed folder alone: before, a new OOTRR release or a puppet pack made after the seed removed it (it has no seed file in `oot-remake-randomizer` to build it again), and the kit's size-table merge (merge_tables.py) now treats it like any other mod: when its table wins, the puppet pack's entries are merged in (its own kept in `_coop-size-table`), and when the pack's wins, the seed's entries go into the pack's. Before, every `randomizer-*` folder counted as one of ours (built beside every table) and was left out, so with a hand-put seed the puppets were held. A table not merged (no Python, or a seed dropped in after the start) counts as an outside one: the puppets are held, and the chat says so, until the next kit start merges it.

Since 0.11.2 the kit's start fixes the table itself (#48): before the game starts, `tools/puppet_pack/merge_tables.py` finds the mod whose size table the game will read (the Mods tab's order from `coop-mods.list`, else by name, as Longshot indexes them), and when that is not one of our seeds or the pack, writes ONE table there: that mod's own entries plus every entry of every other mod that is on (the puppet pack's too; the larger size where two have one). When the pack's table is the one the game reads (a mod the Mods list does not name sorts under `contents\` by name, as "bestbuddy" does), the other mods' entries go into the pack's table the same way (our seeds' not: they are built beside every table); before 0.11.3 they were left out, and a mod that makes game files larger (RSDB tables, for example) made the game abort one second into the start (player report 101). The window says which mod and what was merged in. The mod's own table is kept in `<mod>\_coop-size-table\` (Longshot skips folders whose name starts with `_`), with `merged.txt`, the files merged and the file written (path, length, hash); `merge_tables.py --undo` puts the original back (only over the merged table: a new seed put into that folder since keeps its own). A mod switched off, or no longer the one the game reads, keeps its merged table and mark until then; the game does not read it, and switched on again it is merged again from the kept original. Last it writes `<mod>\coop-merged.txt` (`coop-merged 1`, `table <file name> <hash>`, `pack <hash>`: FNV-1a 64 of the table written and of the puppet pack's): while both still match, the game keeps the puppets on and says nothing; when either changed (the pack made again, another seed put into the folder), the next kit start merges again, and until then the game holds the puppets as above. Starting the game without the kit (longshot.exe directly) skips the merge. The site's seed is still not shared: every player puts the same seed folder into their own `mods`.

Since 0.11.6 the same start also carries the puppet pack's rows in the game's actor tables (player report 144). The pack adds rows to `RSDB\ActorInfo` and `RSDB\GameActorInfo` (CoopPuppet_*, CoopShot_*, ...), and the game reads each of those files from one mod only, the one that wins as above. An OOTRR seed made with settings that change actors (a Settings string, for example) ships its own copies, built from the game's tables without our rows, so the game refused every puppet: name tags, no bodies. Now, for each table the pack ships, the winning mod's copy (our own seeds too) gets every pack row it lacks (its own rows stay), its own copy is kept in `<mod>\_coop-rows\` (`merge_tables.py --undo` puts it back), the size table the game reads gets that file's larger size, and `<mod>\coop-rows.txt` marks it for the game. A mod under `contents\<title id>\` (where emulators keep a title's mods) is merged the same way since 0.11.12; before, it was never rewritten, and Classic Link Voices there, with its own size table, made the game abort at every boot beside Character Select (player report 259: the game read its table without the merged actor tables' sizes). In the game, when such a table wins without that mark (the game started without the kit, or a seed built during this run), the others show as their fairies and the chat names the mod: restart with Start Squadala.

Since 0.11.9 the same start also puts together the files two mods of yours share (player report 206: a randomizer seed and Character Select, both on). The game reads each file from one mod, the first row that has it, so the lower mod's part of a shared file was lost while the rest of that mod still loaded: with a seed first, Character Select's saved picks, its player rows and its menu texts; with Character Select first, the seed's item actors and its changed defaults. Three kinds of file are merged, each into the copy of the mod that wins it, with what every lower mod changed or added (told from the game's own file) where the winner left it as the game has it: the rows of an `RSDB` table (`_coop-rows`), the members of a message or layout archive under `Mals` and `UI\Layout2Archive` (`_coop-archives`), and the values in the game's list of saved values, `GameData\GameDataList` (`_coop-gamedata`). The winner's own copy is kept in that folder beside its `romfs`, the merged file's size goes into the size table the game reads, and the order the mods were put in or the seed was made in does not matter: it is done again at a start whenever one of the files changed. A mod that is switched off, taken out or moved over the one it was merged into leaves nothing behind: at the next start the other mod's own file is put back (or merged again with what is still on), so Character Select without the randomizer plays with its own files, not the seed's defaults. Where two mods changed the same row, member or value, the upper mod's stays and the start's output names it. Two mods that each add saved values of their own (two save layouts) cannot be put together: the start says so and leaves the files alone; turn one of them off. A seed's hash for the other players (below) is taken from its own kept copies, so merging does not make it "another world". Checked on the real files of an OOTRR 0.8.0 seed and Character Select v0.2.1 (no row, member or value is changed by both); not played yet.

This does not change what another randomizer program checks before it installs a seed. The separate "OoT Randomizer" with the Archipelago apworld (github.com/Mozencaz/OotrR) refuses to install into a `mods` folder where another mod has one of the seed's files ("Resources shared with: OoT Character Select. Move these mods out of the title folder, then generate again."). To use it: close the game, move `mods\OoT Character Select` out of `mods`, generate, then move it back and start the game with Start Squadala, which merges the two. Not tried with that program's seeds yet: if its seed adds saved values of its own, as Character Select does, the start says the two cannot be put together, and then only one of them can be on.

Since 0.11.6 the pack also holds the title's co-op rows and the pause menu's Multiplayer tab: larger copies of files the game reads at boot (each language's `Mals` archive, the Title and Common layout archives), with their sizes in the pack's size table. A mod whose table wins and lacks those sizes would make the game fail to load its language archive and crash at boot, so the same start (after the merge) checks the table the game will read: while it lacks them, the pack's menu files wait in `coop-puppet\_coop-menus` and the game shows its own menus (co-op works from the Minus menu); the start says which mod it is. Turn that mod off, or merge the pack's entries into its table, and they are back at the next start.

For OOTRR's extra settings, use the Settings string: copy the settings string OOTRR's own page shows (it starts with `OOTRR`, for example `OOTRR1-EYAQCTABAHIHE`), then in Mods > OoT Remake Randomizer > Settings string press Left / Right (Paste) or, typing, Ctrl+V. When it is set it is used in place of Settings (`ootrr generate <settings string> <seed>`), the seed is built in the Mods tab as any other (with the puppet pack's size entries, in a folder `randomizer-<seed>-s<8 hex digits>`), and in co-op the host's string reaches every guest with the seed, so each guest builds the same seed. A value that is not a settings string is said once in the chat and Settings is used. Empty it to go back to Settings. The kit's OOTRR must know every setting in the string: one it cannot apply yet stops the build with OOTRR's own error in the chat (as a preset it cannot build).

## For mod authors

### mod.json

```json
{
  "id": "camera-tweaks",
  "name": "Camera tweaks",
  "version": "1.0.0",
  "author": "you",
  "description": "One line for the tab.",
  "coop": "own",
  "code": {"windows": "camera.dll"},
  "api": 1,
  "settings": [
    {"key": "distance", "name": "Distance", "type": "number", "min": 1, "max": 9, "step": 1, "default": 4},
    {"key": "mode", "type": "choice", "choices": ["near", {"value": "far", "name": "Far away"}]},
    {"key": "label", "type": "text", "max_length": 16},
    {"key": "smooth", "name": "Smooth", "type": "toggle", "restart": true, "help": "Shown under the row."}
  ]
}
```

- `id`: 1 to 48 of `a-z 0-9 . _ -`, starting with a letter or digit. Without a `mod.json` the folder's name gives it.
- `coop`: `everyone` (default: every player needs the same mod) or `own`.
- `code`: a path inside the mod's folder, or one per system. `api`: the interface version the code was written for; a loader with an older one refuses the mod.
- Settings: `toggle` ("0"/"1"), `choice`, `number`, `text`. `restart`: a change counts after a restart. `shared`: the host's value in co-op.

### Writing a code mod

Include `hookshot/src/coop_mod_api.h` (plain C, no other header) and export `coop_mod_start`:

```c
#include "coop_mod_api.h"

static const CoopModApi *api;

static void frame(void *user) { /* every frame, on the game's calc thread */ }

static int key(void *user, uint32_t vk, int down, int repeat) {
    if (vk == 0x76 && down && !repeat) { api->log(api, "F7"); return 1; }  /* 1: taken */
    return 0;
}

COOP_MOD_EXPORT int coop_mod_start(const CoopModApi *a) {
    api = a;
    char v[16];
    if (api->setting(api, "distance", v, sizeof v) < 0) return 0;
    api->on_frame(api, frame, 0);
    api->on_key(api, key, 0);
    return 1;
}
```

The table (version 1, and versions 2 and 3 below): `log`, `main_base`, `read`, `write` (guest addresses; offsets in our docs are from `main_base`), `setting`, `on_frame`, `on_overlay` (rectangles and text over the picture), `on_key` (key downs on Hookshot), `on_setting`, `hook` and `has_hook` (game functions of the runtime's hook list, before and after, with the registers), `restart_needed`. Register only inside `coop_mod_start`. Keep each callback short; never wait on the game. Calls that take `self` want the table you were given. A later version only adds entries at the end: check `api->version`.

Mods are loaded first row first and started at the first frame. `coop_mod_stop` (optional) runs at exit.

### Menu screens (version 2)

Version 2 adds the game's menu screens. A mod written for it says `"api": 2` in `mod.json`; a mod for version 1 loads and runs as before, and when no mod asks for screens the module reads none.

- `on_screen(api, fn, user)`: `fn(user, screen)` at every menu screen's update, on the game's thread that updates it, before the screen's own update (the HUD is a menu screen too). `screen->kind` is `COOP_MOD_SCREEN_TITLE`, `_LOAD_LIST` (the list of saves the title's Continue and the System page's Load open), `_LOAD_QUESTION` (its question after a save is picked) or `_OTHER`. `screen->focused` is the focused button's name in the screen's layout (`Pa_Button_00` is the title's Continue), `""` when none. `screen->save_list_ready` is 1 when the game's save list is read. `screen->buttons` is player 1's buttons as the game would get them before any hold (a pad, the keyboard's bindings and a click alike). A screen under another one (the title under its load list) keeps its focus too: a mod that takes a button's press checks that no other screen is up.
- Inside that call, and only there, for the screen it hands over:
  - `choose_focused(api)` chooses the focused button the game's own way, as the player's A (its sound, what it opens). 0 when nothing is focused, the button cannot be chosen yet (try at a later update) or co-op is busy: hosting, joining, in a session or the host's save on its way (on every screen, not only the title).
  - `reload_save_list(api)` has the game read its save list again from the save folder, after the mod changed the files in it. The game reads it at the title's next update; `save_list_ready` is 0 until then. It answers 0 when the title is not up (the game reads its list only there), so on the pause menu's System > Load ask again once the title shows.
  - `hold_input(api, buttons)`: the game does not get those buttons from player 1 (`COOP_MOD_HOLD_ALL`: all of them and the sticks, for the mod's own screen in front; a few, such as A on a focused button, to take that choice: the mod sees the press in `screen->buttons` and acts itself; 0 gives everything back). Each call ties the hold to the screen it is made on. It ends by itself when that screen has not updated for half a second (it closed; the HUD and other screens do not keep it) or updates as another kind of screen, and when the mod is switched off. To keep a hold on the next screen, call `hold_input` again there.
  - Called anywhere else they do nothing and answer 0, with one line in the log.
- A hold covers player 1's pad, the keyboard's bindings and a click (it comes as a press), not the mouse's hover over the game's buttons.
- While co-op's own Multiplayer page shows on the pause menu, the mods get no screen updates: the screen behind it is not the player's, and the page takes the pad first. A hold made before ends half a second after the page shows.
- A save screen's file select that the title's Continue and New Game both open says `"file_select": true` in `mod.json` (true or false; off when left out). While such a mod runs and has asked for the screens, co-op's own title menu shows one **Start** row for both; without one (any other menu-screen mod included) it shows **Continue** and **New Game** each, so New Game is always reachable.

### Game sounds and a ready button (version 3)

Version 3 adds two things to the menu screens. A mod that uses either says `"api": 3` in `mod.json`, so a co-op that has only version 2 refuses it cleanly instead of the mod reading past that co-op's table. A mod for version 1 or 2 loads and runs as before.

- `play_sound(api, name)` starts one of the game's own menu sounds on the screen being updated, as its own screens do: `button_on` (a cursor step), `button_decide` (a choice), `Pa_Button_00_decide` (the title's Continue), `mc_TabToRight` and `mc_TabToLeft` (the pause menu's tabs). Letters, digits and `_` only; 1 when the screen had that sound and the game started it. Only inside the mod's own `on_screen` call, as the version 2 calls.
- `screen->focused_ready` is 1 when the focused button takes a choice now: the title has Continue focused while its opening scene plays and its menu fades in, and it is 0 then (the player's first A goes to the title, to bring its menu in). Read it only when the table's `version` is 3 or more.

The mod never sees an address: the module finds the game's functions itself (the button's decide, the save list's read, the screens' classes). The same entries are meant to carry over to the add-on interface of co-op 1.0, where only the runtime under them changes. On Hookshot the screens come through patch 0030's menu screen hook; no other game patch is needed.

A whole sample is in `hookshot/samples/hello-mod` (`mod.json` + `hello_mod.c`; the tests build it as `hello_mod.dll`): copy both files into `mods\hello-mod`, start the game, and F7 shows its message in the corner.

The interface is ours, modelled on NX2navi's plugin interface, and does not depend on Longshot: the same mod is meant to load on any game our module runs on.
