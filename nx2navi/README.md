# nx2navi/

Co-op as a mod of the NX2navi PC port, a static recompilation of the game. The port's source is not in this repo; the one file copied from it is its plugin interface header, whose notice allows that (`dll/third_party/plugin_api.h`, listed in [`THIRD_PARTY_NOTICES.md`](THIRD_PARTY_NOTICES.md)). Otherwise this folder only uses what its docs and source say about how it maps the game's memory, how its launcher runs mods and what its plugin interface offers. The game is not rebuilt for co-op, so this is far less than the emulator build:

- **Every NX2navi build:** joining a session and sending your presence work; the others' joins, chat, scenes and distances go to the log.
- **An NX2navi build with its plugin interface** (the executable exports `nx2navi_plugin_api`, NX2navi `docs/plugins.md`) also gets an **in-game panel** (connection, you, each other player's scene and, in your scene, the distance and a world-axis direction), **notices** (joins, leaves, chat, connection), a **chat box**, and **the other players as a second Link** that stands where they are, turns as they do, moves in their pose bone for bone and wears their gear, only while that player is connected and in your scene ([Puppets](#puppets-nx2navi-with-its-plugin-interface)). It also **takes you to another player**: `/teleport <name>` in the chat box, once to the host when you get into the game, and after the host through every exit the host takes ([Going to another player](#going-to-another-player-nx2navi-with-its-plugin-interface)). With interface version 3 the game's **title screen has a "Multiplayer" entry** ("Multijoueur" in a French game) that opens a page in the game's own settings screen, to host or join without the launcher ([Multiplayer on the title screen](#multiplayer-on-the-title-screen-interface-version-3)), and **a joiner gets the host's save** before it loads anything ([The host's save for a joiner](#the-hosts-save-for-a-joiner)). With version 4 each other player has their **name over their head**. Still not drawn: their Navi.

What is missing and what the port would have to offer for it is [below](#what-does-not-work-and-what-it-would-take).

## Build

```
python nx2navi/build.py            # build\nx2navi-mod\OoT Co-op\ is the mod folder
python nx2navi/build.py --tests    # also builds and runs every test below
```

It looks for the compiler the NX2navi launcher installs (`%LOCALAPPDATA%\Programs\NX2navi\toolchain\msys64\ucrt64\bin`, clang++ or g++), then `C:\ProgramData\mingw64`, then `g++` or `clang++` on `PATH`; `--compiler <path>` names another. ENet is fetched with git at the commit [`cmake/enet.cmake`](../cmake/enet.cmake) pins (doctest likewise, for `--tests`) into `build\nx2navi\`, and the build stops unless git reports that commit for the checkout. Both programs are linked statically, and the script fails if one of them imports a libstdc++, libgcc or winpthread DLL.

With CMake: `cmake -S . -B build -DCOOP_BUILD_NX2NAVI=ON`, then build as usual; the mod folder is `build\nx2navi-mod\OoT Co-op\`. This path was written without a CMake at hand and has not been run yet.

The mod folder:

```
OoT Co-op\
  mod.json
  launcher_plugin.py
  README.txt, LICENSE.txt, THIRD_PARTY_NOTICES.md   (the repository's notices, then this mod's)
  bin\coop_nx2navi.dll
  bin\oot-coop-server.exe      (server\ of this repo, the kit's coop_server.exe)
  tools\puppet_pack\*.py       (the pack tool, Python only)
```

Put it into `<game folder>\mods\` and enable it in the launcher. The menus write `coop.ini` and `settings.json` into it and the DLL writes `coop-nx2navi.log` there; a host started inside the game adds `coop-server.log`, a join `coop-save\` (the host's save, [below](#the-hosts-save-for-a-joiner)). None of these ship: the release maker's list refuses them. With "Show Other Players" on, the first Host or Join also makes `romfs\` (the puppet pack, about 1.5 MB) and `coop_puppet.json` in it, on that PC, from the game's own files: the mod as built and handed out holds no game data.

## The launcher plugin

One home row, **Multiplayer**, opens a menu with four entries: **Host over Steam**, **Host over Local Network**, **Join over Steam**, **Join over Local Network**. The two Steam entries are shown and cannot be chosen (a value row "not available yet", with the reason): Steam needs Valve's Steamworks SDK, which is not in this project, and nothing is faked. The code keeps the two apart (`TRANSPORTS`, `transport_available`): a Steam transport would take its name from the Steam persona name and a lobby or invite in place of the address, port and password rows. The two Local Network entries are the screens below (called Host and Join in the rest of this text), and they are where the player name is chosen. Both do what the emulator kit's `Host.bat` and `Join.bat` do ([`tools/release/kit/scripts`](../tools/release/kit/scripts): `play.ps1`, `start-server.ps1`, `hosting.ps1`, `coop-ini.ps1`), with menu rows in place of the console questions and the same rules for a name (1 to 16 characters), a join password (no spaces, at most 128 bytes) and an address (`ConvertTo-JoinAddress`: spaces, quotes, `udp://` and a trailing dot are dropped, `ip:port` sets the port, a new address without a port means 27510).

- **Host** starts `bin\oot-coop-server.exe --port <port>` in its own console window, with `--password-env OOT_COOP_SERVER_PASSWORD` when a join password is set (the password is in that window's environment, never on a command line), and `--allow` / `--bind` from the settings keys `server_allow` and `server_bind` (no menu row; the kit has them in `coop-options.ini`). It does not start a second server while this mod's server runs, whoever started it. It then shows the addresses to give to friends (this PC's own, best first: the home network's, from a network card with a default gateway, then VPN addresses, then other private ones, then those of virtual cards such as Hyper-V's and WSL's, which are said to be no use to friends; the best one copied to the clipboard; until coop-dll 0.5 VPN addresses came first and a virtual card's address could be the one copied), writes `coop.ini` with `server = 127.0.0.1` and starts the game.
- **Join** writes `coop.ini` with the host's address and starts the game. "Connection" in the Multiplayer menu then reads the DLL's log: connecting, connected, or why the server refused.
- **Shared Progress (experimental)** writes `share_progress = 1` (below).
- **In-Game Overlay** (on) writes `overlay = 1` or `0`: the panel and chat box in a game with the plugin interface; a game without it plays the same either way.
- **Show Other Players** (on) writes `puppet = 1` or `0`. On, and with no pack in the mod folder yet (or one made by the emulator kit's tool, which this port cannot use: [Puppets](#puppets-nx2navi-with-its-plugin-interface)), Host and Join first run `tools\puppet_pack\build.py --romfs <game folder> --mod-dir <mod folder>` inside the launcher (Python 3.14's own zstd, or the `zstandard` package). It reads six to thirteen files out of `<game folder>\romfs\romfs.bin` and writes only into the mod folder. A failure is said on screen and the game still starts, without puppets. The game reads a mod's `romfs\` at its start, so the pack shows from that start on. **The pack is also made when the launcher starts with the mod enabled** (in the background, without a word on screen): a player who hosts and joins only from the game's own Multiplayer page never passes Host or Join here, and the DLL cannot make it (it is Python, and the game has read its files by then). The DLL looks for a pack made for this port before a session starts (its own mod folder, then every folder of the game's mods folder); without one the puppets are off for that run and the log says how to get them (`puppet: off: no puppet pack in the mod folder yet ...`).
- `minimap = 0` in `coop.ini` (no menu row; the launcher's file does not write the key, so it is on) turns the other players' dots on the minimap off.
- **Shared Enemies** (on) writes `objects = 1` or `0` ([`dll/objects/INTEGRATION.md`](dll/objects/INTEGRATION.md)).
- **Follow The Host Through Exits** (on) writes `follow = host` or `off`; **Join At The Host** (on) writes `join_at_host = 1` or `0` ([Going to another player](#going-to-another-player-nx2navi-with-its-plugin-interface)). `follow = anyone` has no menu row: set `"follow": "anyone"` in the launcher's settings of this mod and the toggle keeps it.
- **Use The Host's Save** (on, Join only) writes `host_save = 1`: the game takes the host's save first and starts again on it ([The host's save for a joiner](#the-hosts-save-for-a-joiner)). Host always writes `host_save = 0`.
- The game is started with `api.play(env={'OOT_COOP_INI': <mod>\coop.ini}, dlls=['bin/coop_nx2navi.dll'])`. `mod.json` lists the DLL too, so the launcher's normal Play also loads it: **without `OOT_COOP_INI` in the environment the DLL idles**, whatever `coop.ini` holds from an earlier session, and the title screen's Multiplayer entry is the way in. With it, Host and Join start the session at once, as before.
- The settings file is shared with the game's own page: this menu keeps the keys it does not know (the page's language) through its saves, and uses a password typed in the game (kept under Windows' data protection, `join_password_protected` / `server_password_protected`) without writing it out as clear text. A password typed HERE is still kept as plain text, as below.

Where it differs from the kit, on purpose:

- **The server keeps running when the game closes**, as the kit's server window does, so the others stay in the room; "Stop Server" in the menu ends it, and the toggle "Stop Server With Game" (off) ends it with the game.
- **No internet address lookup.** The kit asks api.ipify.org for the public address; the plugin asks nothing outside the PC and only says how to find it.
- The settings are kept with the launcher's `load_settings` / `save_settings`, the passwords included and as plain text, as the kit keeps them in `coop.ini` and `coop-options.ini`.
- No server log file (the kit's PowerShell wrapper writes one), no updater, no firewall check (`check-hosting.cmd`).

The launcher API the plugin uses: `mod_dir`, `log`, `add_home_row`, `action`, `value`, `toggle`, `text`, `divider`, `show_menu`, `refresh`, `message`, `play`, `game_running`, `start_process`, `on_game_exit`, `load_settings`, `save_settings`. `start_process` gets the whole environment plus the password variable, so it works whether the launcher adds `env` to its own environment or uses it as given.

## The DLL

### How the game's memory is reached

NX2navi maps the game's memory at the game's own addresses: a guest address is an address in the `ocarina.exe` process ("guest address equals host address", its `docs/architecture.md`; its loader commits each module at its base and copies the segments there, then makes code and constants read-only: `runtime/loader.c`, `load_module` and `seal`). The modules start at a fixed base, `FIRST_BASE = 0x7000000000` in its `recomp/layout.py`, with `main` first. So:

- `GameMemory::main_base()` is `0x7000000000`, and the offsets of [`coop/host/src/addresses.hpp`](../coop/host/src/addresses.hpp) (game 1.1.1, build `e0f3ccfaf50065ae`, the version NX2navi targets) are added to it.
- Pointers read from the game are used as they are.
- The game's compare-and-swap instructions are host atomics on the same words (its `recomp/lifter.py`), so the DLL's locked compare-exchange is atomic against them.

Before anything is read, the DLL checks what is at that base (`CheckMain`, [`dll/guest_memory.cpp`](dll/guest_memory.cpp)): committed memory, the module header (`MOD0` at the offset stored at base + 4), and the GNU build id note in main's read-only data, which must be `E0F3CCFAF50065AE...`. It looks every second until the game has loaded. Another build is logged once and nothing is read or sent about the player; so is a process that is not the game.

**In a game with the plugin interface, the game's memory is touched on the game's own thread only**, through the interface's `read`, `write` and `map_range`: the local player is read in the game-thread callback (the frame step hook, below), the map's view in the map screen's own update, and what the game is (its base and build id) comes from the interface's `game_info`. No thread of the DLL reads, writes or asks Windows about the game's pages. That is not a matter of taste: see [Frame rate](#frame-rate).

**In a game without the interface** (an NX2navi build from before it) the DLL is a foreign thread: the game runs while it reads. Every read asks Windows what is mapped first (`VirtualQuery`; guard pages are left alone) and then copies through `ReadProcessMemory` on its own process, which fails quietly when a page has gone and raises no exception, so the port's own fault handlers never see it. Reads are kept by page for one frame. Writes (shared progress only) go only into committed read-write memory. This path is unchanged and, in a build whose renderer tracks the game's pages as the current one does, it is slow (below); it is kept because such a build has no other way in.

### Frame rate

Until coop-dll 0.5 the DLL made the game unplayable: **30.0 frames a second without it, 5.0 with it** (solo, standing in Hyrule Field, `launcher-test\run_mod.py`'s settings with the 30 fps limit; measured by the runtime's author, `NOTES.md` 23:58). The cause was the DLL's own 60 Hz thread reading the local player from outside: each frame it asked Windows about some dozens of pages (`VirtualQuery`) and copied them through the kernel (`ReadProcessMemory`), and those calls work on the process's address space while the runtime changes page protections all the time to follow what the game writes for the GPU. The game's own time for that tracking went from 0.6 to 17 ms a frame and its GPU replay to 280 to 500 ms a frame. Found by leaving parts out: with puppets, panel, minimap, name tags, follow and the join at the host all off, and only that thread's reads left, the game still ran at **3.2** frames a second (run `b1`).

Since coop-dll 0.6 the session's frame (reading the player, the life, the scene, shared progress's flags, and handing the result to `coop::host::Session::frame`) runs **in the game-thread callback**, first thing, before the puppets' and teleport's work, with the callback's own access to the game's memory. The DLL's own thread no longer reads anything: it looks for the interface, serves the save transfer and, when the game's thread made no frame for a second (a long load, a stopped game), makes a frame with no reading so the session stays alive and the others see "not in game". Measured with the same settings (the second minute of each run, the game's own `frametime: 60 s` line):

| Run | Frames a second | 1% low |
|---|---|---|
| no DLL (`f_b`, the runtime's) | 30.0 (the limit) | 24.4 |
| coop-dll 0.5, solo (`f_c`, the runtime's) | 5.0 | 3.9 |
| coop-dll 0.5 with only the thread's reads (`b1`) | 3.2 | 3.9 |
| **coop-dll 0.6, solo, everything on (`c1`, and `c3` with a later build)** | **30.0, 30.0** | **24.8, 25.2** |
| **coop-dll 0.6, two games on one PC, each showing the other's puppet: host / joiner (`c2`; `c4`; `c6` with the build that is installed)** | **30.0 / 29.4, 30.0 / 30.0, 30.0 / 30.0** | **23.7 / 16.4, 25.3 / 21.7, 24.8 / 23.7** |
| coop-dll 0.6, two games with shared enemies on (`objects = 1`, 22 copies held; `c5`) | 30.0 / 30.0 | 24.2 / 22.1 |

The game-thread callback takes 0.08 ms a frame solo (about 350 reads), 0.13 ms with a puppet, and 0.36 ms plus 0.07 ms for the objects' own step with shared enemies on (the status line in the log says it every 10 s). If the interface gives no callback on the game's thread at all (none free), the DLL says so after five seconds and reads from its own thread as without the interface, rather than go blind. `OOT_COOP_READS=thread` in the environment puts the reads back on the DLL's own thread and `OOT_COOP_READS=off` leaves them out, to measure again.

Not changed: a game with interface version 1 (the frame callback, no fast memory) still asks Windows about a run of pages at most once a second on the game's thread (`puppet.cpp`), because that version's own `read` took 0.9 ms a call; and a game with no interface reads from outside as before.

### What it does

On load `DllMain` only starts a thread, which writes `coop-nx2navi.log` in the mod folder (found from the DLL's own path). What it does next depends on how the game was started:

- **`OOT_COOP_INI` names a `coop.ini`** (the launcher's Host or Join, the mod's own restart into the co-op save, a test): the session in that file starts at once. A missing file, no server in it or a mistake in it is said in the log, and the DLL idles as below.
- **No `OOT_COOP_INI`** (the launcher's normal Play): the DLL **idles**. It takes the plugin interface, puts the Multiplayer entry on the title screen and registers the exit callback; no connection, no thread of the session, no read of the game's memory, no hook, no puppet. The log says `idle: no session yet ...`. Start or Join on the page then starts the session in the running game.

`OOT_COOP_PASSWORD` in the environment replaces the file's password (the mod's own restart passes it that way, so the game never writes a password into `coop.ini`).

```ini
server = 192.168.1.20
port = 27510
name = Saria
password = three-random-words
share_progress = 0
overlay = 1
puppet = 1
follow = host
join_at_host = 1
objects = 1
```

The first four keys are the emulator's and are read by the emulator's own code ([`lichii/hook/coop_settings.cpp`](../lichii/hook/coop_settings.cpp)); `share_progress` (off unless 1), `overlay`, `puppet`, `minimap`, `name_tags` and `join_at_host` (on unless 0), `follow` (`host` unless `anyone` or `off`) and `host_save` (off unless 1: a joiner takes the host's save first) are this port's, and so are `objects` (on unless 0, since coop-dll 0.7: shared enemies and boss rooms) and its switches `objects_boss`, `objects_world` (on unless 0), `objects_ai_hold` (3 unless 0, 1 or 2), `objects_friendly` (off unless 1: townspeople and animals shared too) and `objects_rolls_apart` (30: the metres from the first player beyond which a player's game rolls its own Stalchildren; 0 = never): [Shared enemies](#shared-enemies).

| Thread | What |
|---|---|
| The DLL's own, 60 a second | Looks for the game until it is found (with the plugin interface: asks it; else looks at the memory at the base). Serves the save transfer. **Without the interface** it also makes the session's frame: reads the local player from outside and hands it to `Session::frame`. With the interface it makes a frame only when the game's thread made none for a second, with no reading. |
| Network | `Session::service`: connects (HELLO, the join password's proof, reconnects), sends what the frame queued, feeds what comes in to presence. Joins, leaves, chat and refusals are logged. |
| The game's presenting thread | (plugin interface only) The overlay callback: copies the panel's lines under the overlay's lock and draws them. |
| The game's own thread ("game thread") | (plugin interface only) Everything that reads or writes the game's memory or calls a game function. First **the session's frame**: the local player is read (`PlayerReader`) and handed to `Session::frame`, which runs the `Sampler` and queues `PLAYER_STATUS` and `PLAYER_SAMPLE`; every 10 s a status line goes to the log (ping, your scene, each other player's scene and distance from presence). Then the puppet director's step and its calls (`puppet = 1`), then teleport's. With interface version 2 it is a hook of the game's frame step `main+0x3b4e300`, taken only for the two calls from `moduleCalc_` (the emulator build's own point); with version 1, or with `OOT_COOP_FRAME_HOOK=0` in the environment, it is the frame callback on the presenting thread. The log says which (`game thread: hooked the game's frame step ...` or `game thread: frame callback registered ...`), and so does the `status:` line. |
| The game's window thread | (plugin interface only) The key and text callbacks: the chat box and the hide key. |

The log lines `coop: on, server ...`, `coop: welcomed as player N ...` and `coop: server refused: ...` are the emulator's, so the launcher's "Connection" row reads them as the kit reads the emulator's log.

When the game ends in an orderly way (its window is closed, it restarts, it exits) the interface's exit callback (version 2) stops the session with a goodbye to the server, stops the server this game started, and starts the game again when the mod itself closed it for the co-op save. A game that is killed or crashes ends the DLL's threads without notice: the server lets the player go after its timeout (the client's "name taken" retry covers a quick restart), and the server this game started ends with it (a job object). `coop_nx2navi_stop(wait_ms)` does the same by hand; only tests call it.

### The in-game overlay (NX2navi with its plugin interface)

**Getting the interface, and the fallback.** The DLL exports `nx2navi_plugin_init`, which the game calls for every library in `NX2NAVI_MOD_DLLS` before its own code runs (the launcher sets that variable for `api.play(dlls=...)`). The DLL keeps the table and nothing else there. If the game never calls it (the DLL came in only through the launcher's injection), the frame thread asks the executable's `nx2navi_plugin_api(1)` once the game's `main` is found, never from `DllMain` (NX2navi `docs/plugins.md`). A game whose executable has no such export is an NX2navi build from before the interface: the log says so once (`overlay: this game has no plugin interface ...`) and co-op runs exactly as without it. The DLL may be loaded twice (injected, then named in `NX2NAVI_MOD_DLLS`): Windows loads one module, `DllMain` runs once, and a second `nx2navi_plugin_init` is ignored. The overlay's callbacks are registered only when co-op is on (a server in `coop.ini`) and `overlay = 1`; the game-thread callback whenever co-op is on (teleport needs it with `puppet = 0` too; alone in the room it calls nothing). The game then pins the DLL. The DLL asks the executable for version 2 first and for version 1 when that is refused.

**What it shows**, at the bottom left (clear of the hearts, the item buttons and the map), on a black background at about 60% opacity, sized from `Nx2Draw.text_height` and `scale`:

```
Co-op: connected as P1 "Saria"          (or: connecting to <server>... / server lost, retrying <server> / refused by the server (<why>))
You: spot00                             (or: not in game (title screen, load or menu) / game not found yet)
P2 Mido: spot00, 12.3 units, north-east (same scene: distance and direction)
P3 Zelda: Field_spot01                  (another scene)
P4 Ruto: not in game                    (no sample for 2 s: title screen, a load or a menu; the wire does not tell them apart)
Mido joined                             (notices: joins, leaves, chat, connection; fade out after 6 s)
Enter: chat   F9: hide
```

- **The distance** is between your position and where presence shows the other player now, in the game's units, only when both scenes are known and equal. **The direction is world-axis based, not camera based**: north is world -Z and east is world +X, eight sectors, and "right here" under half a unit apart horizontally. That -Z is the top of the game's map is an assumption that was not checked; nothing turns it with your camera.
- **F9** hides and shows the panel (the runtime keeps F1, F8, F10, F11, Insert, Esc and Alt combinations for itself; F9 has no game button by default, NX2navi `runtime/input_map.c`; a player who bound F9 to a button gets both). While hidden, nothing is drawn and Enter does not open the box.
- **Chat:** Enter opens a one-line box (`capture_input(1)`: the game gets no input while it is open), typed characters come through `on_text` (control characters dropped, at most 200 code points, the protocol's `kMaxChatChars`), Backspace takes one character out, Esc cancels, Enter sends with the protocol's `CHAT` (`Client::send_chat`, which checks the protocol's rules again) and gives the input back. Your line is shown at once (the server does not echo chat). While the box is open the notices make room for the last 8 chat lines. Enter does nothing while the game's own menu is open.
- **No Tab list:** the panel already lists every player, and Tab is the game's Plus button by default.
- **A colour per other player:** green, blue and yellow, given to the up to three others in the order of their player numbers with your own left out (`Ui::PeerColour`), so every screen shows its three others in the three colours; never red, which is the colour of the game's own marker for yourself. A player's line in the panel, their chat lines and notices that start with their name, and their dot on the minimap have that colour. The colours are per screen: the same player can be green for one player and blue for another. Nothing on Link or on a puppet is recoloured.

**The other players on the minimap** (`minimap = 1`, the default; interface version 2). Each other player in your scene whose samples arrive is a dot in their colour on the field's small map, with a black rim. Nothing of the game's own map is changed (the game's marker for yourself stays as it is). How (read from `main` and the layout files; the numbers checked in one run, below): the map screen `UIMapMenuScreen` is the minimap and the full map in one; its per-frame update main+0x33e12c0 is hooked only to learn the screen object and that the map is being updated. From the screen: the icon controller at +0x390 holds the world x and z at the picture's centre (+0x160, +0x168) and the world length the picture shows (+0x16c), set by the game from the scene's map capture; the small field picture's pane is at +0x1498 (place at pane +0x4c/+0x50 in the layout's 3840 x 2160 canvas with its origin at the centre, size at +0x58/+0x5c, scale at +0x28/+0x38); the byte at +0x2350 is not 0 while the small map is the one shown. The map is north up (+X right, +Z down). Those values are read on the game's thread, inside the map screen's own update (the hook), and handed to the thread that draws. A dot is drawn only when every one of those reads, the numbers are sane, the map's update ran in the last half second, the small map is the one shown, the game's settings menu is closed, your Link is in the game and no cutscene or talk runs here; a player outside the picture gets no dot (never one pinned to the edge). Not handled: dungeon and indoor maps (another layout and floors: no dots there) and the full-screen map. In a window whose picture has black bars the dot is placed in the picture's rectangle (interface version 4 tells it; an older game places it for a picture that fills the window); written after a run showed the dot in the bar, and not looked at since. `OOT_COOP_DEBUG_MINIMAP=1` also draws your own position as a white dot, to compare with the game's arrow, and logs what was read once a second.

**Name tags over the other players** (`name_tags = 1`, the default; interface version 4). Each other player in your scene whose samples arrive has their name over their head, in their colour, on a dark plate. The point is the player's shown position plus 1.9 m (1.25 m when your Link is the child: the players of a session share the save, so they share the age), taken to the window by the interface's `world_to_screen`, which knows the game's camera and where the game's picture lies in the window. The tag is centred on that point and sits above it; it is kept inside the picture at the sides and the top, and a player who is behind the camera or outside the picture gets none (never a tag pinned to the edge). **It fades with the distance** from your own Link: full up to 10 units, down to 30% at 40 units and 30% beyond (`Ui::TagAlpha`; it stays readable, since it is the only mark of where a far player is). It is not hidden behind walls. `OOT_COOP_DEBUG_TAGS=1` logs once a second where a tag was drawn. No tags while the game's own menu is open, while a cutscene or talk runs here, or with your Link not in the game. A game that serves an older interface draws none and says so once (`name tags: off (they need the game's camera: plugin interface version 4)`).

**Threads.** One mutex guards everything the callbacks share with the DLL's threads (`overlay.cpp`): the session's frame (on the game's thread with the interface) publishes a snapshot each frame (from `PlayerReader`, the client's room and presence) and takes the typed lines to send; the network thread adds notices; the overlay callback copies its lines under the lock and draws outside it; the key and text callbacks change only the chat box and the outbox. No callback calls the network: sending happens in the session's frame. The player is read on the game's thread ([Frame rate](#frame-rate)); the overlay callback, on the thread that presents, reads nothing of the game: it draws from the snapshot and from the map's view as the game's thread last read it.

**Markers at the screen's edge for players out of view: not built.** The name tags are the marker for a player in view. The camera they would need is there since interface version 4 (`camera`, `world_to_screen`).

### Puppets (NX2navi with its plugin interface)

**What the emulator build does.** One patch set, on while co-op is on ([`lichii/hook/coop_svc.s`](../lichii/hook/coop_svc.s), `coop_svc.cpp`, [docs/puppet.md](../docs/puppet.md)):

- Two instructions in `main` are replaced: the `bl 0x3b4e300` at main+0x6e70f8 (every frame) and at main+0x6e6dd8 (rare), both in the engine's `moduleCalc_`, become `bl 0x3c46280`, a 128-byte routine in the zero padding after the code.
- That routine runs on the game's calc thread once a game frame, after the frame's job graph has been waited on: the actors of the frame have run, no other thread is in them, and the draw has not read them. It loops on `svc #0xf4`: the emulator answers with nothing, or with one game function to call (address, x0 to x7, s0, 0x20 bytes of stack arguments); the routine calls it and hands its x0 back with the next `svc`. At most 256 calls a frame. Then it jumps to 0x3b4e300 as the game would have.
- The `svc` reaches `CoopPuppet::Director::Step` first (then the objects, spawns, fairies and the rest, `CoopSvc::AddCaller`). The director reads and writes guest memory directly and asks for these game functions: `malloc` 0x14c6c90 (a block per puppet for names and requests), `requestCreateActorAsync` 0x372a70 with the actor manager at `[0x4e91888]`, then 0x36fbd0 to take the actor out of the finished request (or 0x36fde0 to drop it), the delete request 0xa6490, the AS play 0x2022a0, the frame setter 0x37b5d70, the slot sync 0x3abec10, the equip call 0x2df7b20, the armor take-off 0x10aceb0 and the in-hand change 0xe34c40. Position and rotation are plain writes each frame (actor +0x31c, +0x328 and the pending transform +0x358, +0x364), and so is the bone-by-bone pose copy (`coop_pose.cpp`).

**How each piece maps here** (`dll/puppet.cpp`):

| Emulator | This port |
|---|---|
| The hook in `moduleCalc_` and the routine in the padding | Interface version 2: `hook_function(main+0x3b4e300)`, the frame step itself, acted on only when it was called from `moduleCalc_` (return address `main+0x6e70fc`, or the rare `main+0x6e6ddc`): the same thread and the same moment as the emulator's routine, before the function runs. Interface version 1 (or `OOT_COOP_FRAME_HOOK=0`): `on_frame`, once per presented frame, on the game's thread that presents, between two frames. Not the same point: see the risk below. |
| `svc #0xf4` and its loop | `Director::Step` called directly in the callback; each call it returns is made with `guest_call_regs` (x0 to x7, s0 as the low word of v0) and its x0 handed back, until the director has no more (at most 8 a frame, its own limit). |
| Guest memory from the emulator | Interface version 2: its `read` and `write`, which are fast for the game's heap, stacks and modules and are checked against the game's own mapping generation. Version 1: direct copies where Windows reports committed, readable (for writes: read-write) pages, asked for at most once a second per run of pages, and the interface's calls for everything else (they alone were too slow there: 0.9 ms a read in the game, see below). |
| Spawn | The same create request, through the game's own thin caller main+0x2ef7600 (below). The director finds the actor as in the emulator: the request's state at the handle slot, 0x36fbd0 to take it, its vtable kept to notice reuse. |
| Position and rotation | The same four writes each frame. They hold: the actor's own calc applies the pending transform. |
| Animation | The pose copy, as in the emulator build: in the frame callback the local Link's skeleton is read (327 bones for adult Link) and sent as `PLAYER_POSE` up to 30 times a second by the network thread, and each puppet's bones are written from the poses its player sends. The AS commands (0x2022a0, 0x37b5d70, 0x3abec10) play only for a player whose poses do not arrive. |
| Gear, in hand or put away | The same calls, from `PLAYER_EQUIP`. |
| Despawn (the player left, another scene, another age) | The same delete request; a scene change of ours deletes the actor by itself and the director sees it gone. |
| "The game draws" (no create during a load) | The emulator knows it from its renderer's camera. Here the player being readable stands for it: the session's frame reports a camera frame for every frame with a player reading (`CoopCamera::Publish`), so the director's own wait (0.75 s of drawing after a scene change) works unchanged. |
| The teleport caller of the cave | Ported (`dll/teleport.cpp`), asked after the director in the same loop: [Going to another player](#going-to-another-player-nx2navi-with-its-plugin-interface). |
| The other callers of the cave (fairy, objects, spawns, time, boss) | Not ported here. They would be asked after the director in the same loop. |

**What does not map, and what is done instead:**

1. **A hook inside a game function.** The port's code is translated ahead of time; nothing can be placed at main+0x6e70f8 when the game runs. With interface version 1 `on_frame` is the only entry, and it comes after the frame was drawn and handed over, not before the draw. Version 2 hooks whole functions, and the instruction at main+0x6e70f8 is a call of one: that is the hook used now.
2. **Stack arguments.** (Version 2's `guest_call_regs` can pass them; the way below works with both versions and is kept.) The create function takes three arguments on the stack (a byte and two pointers, all 0 from every caller read; it writes a status through the second when it is not 0). `guest_call` cannot pass them: the callee would see whatever the presenting function has at its stack pointer. So the create goes through main+0x2ef7600 `(obj, name, argument, source)`, a 43-instruction function of the game that calls the create function with `obj + 8` as the handle slot, x4 to x7 0 and the three stack arguments 0. With `obj = handle - 8` and `source = handle + 8` its two other steps do nothing (it skips a copy when `source == obj + 0x10`, and three field copies land on themselves). One difference remains: its fifth argument is 0 where the emulator's routine passes 1 (stored at request +0x14, meaning not read). Puppets were created, taken and deleted with 0 in every run here.
3. **The moment of the pose copy.** The emulator writes the bones after the game's animation ran and before the draw; `on_frame` writes them after the draw, a whole frame before the next one. It holds all the same: the puppet plays no AS command while poses arrive, and nothing else writes its bones (`pose: ... last write kept 8, overwritten 0` every second of the test, `OOT_COOP_DEBUG_POSE=1`). The AS commands alone are not enough, which is why the copy is on: with them the puppet slid along in one pose while its player ran. `Move` was played (`P2 plays 'Move'`, "returned 0x1") but shows no run on an actor that has no speed of its own, and the frame read from the player's slot (+0xe8) was 12.0 at every sample, standing or running, so it is not a frame to follow. `OOT_COOP_PUPPET_POSE=0` in the environment turns the copy off (AS commands only).
4. **A null read the emulator forgives.** The player's EquipmentUserParam has `IsPouchUser` true, so a new puppet wears the local game's equipment a moment after it is made. With no mask worn the game's take-off call (main+0x10aceb0, index 0) runs main+0x4b8240 on the wearer, which reads its physics component. The puppet has none (on purpose), so that is a read at address 0x20. The emulator returns zeros for it and goes on; the port stops the game: `FATAL: access violation ... reading address 0x20 in lifted function f_70004b8240`, on a worker thread 2 s after the first create (seen 2026-11-12, both games). The pack tool now gives each puppet its own EquipmentUserParam with the player's as `$parent` and `IsPouchUser` false, as the game's Dark Link has it (`--no-pouch`, always on for the port's game files; `coop_puppet.json` says `"pouch": false`). The director's equip calls dress the puppet as before. A pack from the emulator kit's tool (`"pouch": true`) crashes the port; the launcher add-on makes the pack again when it finds one.

**Thread and timing risk (interface version 1 only).** With version 2 the work runs at the emulator hook's own point (above) and this paragraph does not apply. The emulator's hook runs where the engine itself has stopped every job that touches actors. `on_frame` runs in `nvnQueuePresentTexture` on the guest thread that presents, with the other guest threads running (NX2navi `docs/plugins.md`). Whether that thread is the one that runs `moduleCalc_`, and whether the engine's workers are idle at that moment, was not established from the code. What the runs show: in every run here creates, takes, AS plays, equips and deletes worked from it and the game did not fault once the pack was right (about 15 minutes of play over nine runs, two games at once in six of them). That is evidence, not proof: the create request is asynchronous by design and the allocator is the game's thread-safe one, but the AS play, the equip call and the plain writes into an actor are made while a worker could be in that actor. If a crash in an actor function turns up in play, this is the first suspect, and the fix is on NX2navi's side: a callback at the hook's own point (below).

**An ExeFS patch instead?** NX2navi builds `<mod>/exefs/*.pchtxt` and `*.ips` files into the game at its next rebuild (its `tools/exefs_patches.py`): a replaced instruction becomes a switchable site in the translated code, and a branch into zero padding gets the padding's code inlined at the branch. The co-op routine cannot go that way: the inliner refuses a cave with a branch or a pc-relative instruction (ours loops and has `cbz`, `b.mi`), refuses an `svc` or `blr` before its last instruction, and the runtime gives a plugin no handler for an `svc` number anyway. A patch that only redirects the call to another game function does not help either: there is no game function that calls back into a DLL. So a patch file cannot give the hook; it needs the runtime (the list at the end).

**Cost.** In the test games one `read` of the interface took about 0.9 ms and one `write` 1.1 ms (each takes a lock of the game's memory manager), and Windows' own calls on the process were as slow (`ReadProcessMemory` 0.12 ms, `WriteProcessMemory` 1.1 ms, `VirtualQuery` about 1 ms). A live puppet needs about 25 reads and 4 writes a frame: 27 ms a frame with one puppet through the interface, 120 ms with two games running. With direct copies and one page query per run of pages a second, the reads and writes of a frame with one puppet took about 1.3 ms at four queries a second and should take a quarter of that at one (not measured again). The test games were slow as a whole (below), so these are upper bounds, not what a game at full speed pays. The `status:` line in the log says it every 10 s: frame callbacks, their mean and longest time, game calls, reads, writes, page queries, and how many reads and writes still went through the interface.

**When a puppet is there.** Only for a player who is connected, in your scene (a child scene and its adult twin count as one) and sending positions: the planner makes a target from presence and from nothing else. It is deleted when that player's samples stop (2 s after the last one fades), when they leave or the connection is lost, and when either of you is in another scene. Alone in the room no game function is ever called (`0 game calls` in the `status:` line). The one exception is a debug switch, off unless set: `OOT_COOP_TEST_PUPPET=1` in the game's environment puts one more Link 2 m beside you, wearing your own gear, with no second player; the log then says `puppet: on, test puppet beside you`.

**Other switches** (environment, for tests): `OOT_COOP_DEBUG_PUPPET=1` a status line a second per puppet; `OOT_COOP_DEBUG_ANIM=1` every animation, gear and position line; `OOT_COOP_DEBUG_POSE=1` a pose line a second; `OOT_COOP_PUPPET_POSE=0` no pose copy.

### Going to another player (NX2navi with its plugin interface)

Three things, one mechanism (`dll/teleport.cpp`; the rules are the emulator hook's own, [`lichii/hook/coop_teleport.h`](../lichii/hook/coop_teleport.h), over the protocol's `JOIN_PARTNER`):

- **`/teleport <name>`** in the chat box (`/tp` too; the whole name, a unique start of it, or the player's number; `/teleport` alone lists the players). It is a command: nothing is sent as chat.
- **Join at the host** (`join_at_host = 1`, the default): once per connection, 2 s after your Link is first in the game while the host is in the game too, your game goes to the host. The host is the player the server names (the first one in). If the host is not playing within 30 s of your getting in, there is no join later: `/teleport` then.
- **Follow through exits** (`follow = host`, the default; `anyone`; `off`): when a player you follow was in your scene and is then in another one, while your own Link stayed in the scene, your game goes after them. `host` follows only the session's host (the host follows nobody); `anyone` follows every player. The trigger is that one edge (`dll/teleport_auto.hpp`), so:
  - **no loop**: the follower arrives in the leader's scene, which is a change away from nobody's scene;
  - **two players who take different exits at once do not swap**: each has left the shared scene (its Link is not readable during the load) when the other's new scene shows, and leaving the scene forgets who was there;
  - **a cutscene, a talk or a menu of yours** delays it: the want is tried again every 2.5 s for a minute (the trip refuses while an event runs here, and the leader's game answers "busy" until its Link has stood in the new scene for 0.3 s);
  - **another age's scene** (`X_Child` for an adult Link) and **a scene with no known entrance** (`lichii/hook/coop_start_points.inc`: 143 entrances) are refused with a line in the panel; a boss fight is not known to this port (the hook's boss rooms are not ported), so nothing refuses on its account.

**What going there is.** The asker sends `JOIN_PARTNER`; the other game answers by itself with its scene and the place where its Link last stood on its feet (never a spot in mid-air), or refuses (loading, an event). Then, on the game's thread:

- **the same scene**: Link's position is written (actor +0x31c) and the actor's set-matrix function called (main+0x4c6580), as the hook's boss rooms move Link. **You are put beside the player, not on them**: 1.3 units behind and 0.5 to the side of where they stood (behind is where they came from, so there is ground and no wall), turned the way they face (the rotation rows at actor +0x328, about the vertical only). On their very spot the two Links stood in each other and the camera behind yours looked through the other one (a large translucent Link over the whole picture, `launcher-test\f1-follow-sheet.png`). With interface version 5 the mod then asks for the game's own camera reset (`camera_reset`: the runtime presses the game's camera button for the player, so the follow camera goes behind Link at once; with an enemy in reach that press also locks on to it for those frames, as the player's own would); in an older game the camera is not touched and comes round by itself;
- **another scene**: the game's own request flags are written (`Sequence_ReservedNextStartPosName`, then `Sequence_ReservedNextBanc`: what a loading zone's event reserves) and the short event `DefaultParentEvent` is started through the game's event request (main+0xd79f10 builds the argument, main+0xd7a820 asks the manager at `[[main+0x4c7e090]]`, the block from the game's `malloc`), since the game loads a reserved scene when an event ends. The start point is the entrance of that scene nearest the other player, so **after a follow you come in through the door the leader took**: the protocol carries no entrance name, and the leader has just come out of that entrance. Once the new scene has settled (1.5 s) the game asks again and puts you next to the player.

All of it works with interface version 1 (`on_frame` and `guest_call_regs`); with version 2 it runs in the frame-step hook like the puppets. The DLL's own threads only plan and talk to the server: every write into the game and every game call is made on the game's thread. Without the plugin interface the command says so, and requests from the others are refused as "busy".

**For tests** (environment): `OOT_COOP_DEBUG_POS=1` logs your position once a second; `OOT_COOP_TEST_GOTO="<seconds>:<x>,<y>,<z>;..."` moves your own Link there that many seconds after it first was in the game (the same-scene move, without another player).

**After a Game Over** (seen for real: run `g2` under "Verified, and not"). A follower whose Link has no life left (read from its Life component, the place the shared enemies read an actor's life from: `[[actor + 0x270] + 0x2b8]`, the value at `[life + 0x1c10] + 8`) is brought back to the player it follows once the game has reloaded and its Link has stood for 2 s: the log says `our Link has no life left (Game Over) ...`, then `teleport: back from Game Over; going to <name>`. The leader is the host; with `follow = anyone`, the host or else the first player in the game. Not for the host itself, not with `follow = off`, and not when the Link was brought back where it fell (no reload within 90 s: a fairy).

**The black picture after a scene change, and its cause.** Until this build a follow or `/teleport` into another scene left the picture black. The cause was this mod's own write, found by the runtime's trace of the game's sequence nodes: the scene start of the new scene runs under a parent node that tests `Sequence_ReservedNextBanc` every frame, and the game itself empties that flag at the very end of its scene start. The mod emptied it as soon as its own scene reading said the new scene ("arrived"), which is in the middle: the test flipped and the scene start was dropped before the player position was set, the boot event ran, the pause `SceneBeginning` was released and the scene's passes were switched back on. Now the request flags are written only while they are still the mod's: once the game took the request (its load started) nothing is written any more, the "new scene has settled" wait holds until the game has emptied the flag itself, and only a request the game never took is cleared (the give-up path).

The fifth row of each page and the two pages of the second block are the [multiplayer saves](#multiplayer-saves-the-saves-co-op-is-played-on).

Each page holds only the rows it needs (`launcher-test\j2-host-sheet.png`, `j2-join-sheet.png`): the runtime hides the game's unused row templates since interface version 4's last build, so the "Langue" row and the on/off row that pages carried until coop-dll 0.5 only to cover them are gone. "Show Other Players" is the launcher add-on's toggle (`puppet` in the settings file), as before.

- **The two Steam entries** are there and cannot be used ("Indisponible" / "Unavailable", the caption says why): Steam needs Valve's Steamworks SDK, which is not in this project. With interface version 4 they are disabled rows, as the game shows a setting it rules out (dimmed, the cursor passes over them); with version 3 they are buttons that do nothing.
- **Host over Local Network**: the name, the port, an optional join password, and **the address to give to friends**. The addresses are this PC's own, asked of Windows with what it knows about each network card (`GetAdaptersAddresses`), **best first: the home network's (a card with a default gateway), then a gaming VPN's (Hamachi, Radmin, Tailscale), then other private ones, then those of virtual cards (Hyper-V and WSL's "vEthernet", VMware, VirtualBox, Docker: no friend's PC is behind them), then 127.0.0.1** for a second game on the same PC. The caption says which kind the shown one is ("L'adresse de ce PC sur votre réseau local.", "Carte virtuelle (Hyper-V, WSL) : pas celle-ci."); choosing the row copies the one shown to the clipboard and shows the next. Until coop-dll 0.5 the first address was whatever the host name resolved to first, which on a PC with WSL was `172.27.240.1`, a virtual card's. **Start** starts `bin\oot-coop-server.exe --port <port>` from the game, with no window (its output goes to `coop-server.log`), the password in its environment only; a server of this mod that already runs (the launcher's) is used as it is, never a second one. The game then connects to 127.0.0.1, the page closes, and the player loads a save with the game's own Continue. The server stops when the game ends (the exit callback; a job object when the game is killed); one the launcher started is left running.
- **Join over Local Network**: the name, the host's address (`address:port` sets both), the port, the password, **Join**. It connects, takes the host's save and restarts the game on it ([below](#the-hosts-save-for-a-joiner)). A refusal (wrong password, name taken, full room) or no answer is said on the page and Join can be chosen again.
- **The language** is the game's, with no row for it: French for a French game, English for every other. The game's language is decided as the runtime decides it (`NX2NAVI_LANG`, else `lang` in `<game folder>\nx2navi.ini`, else `NX2NAVI_LOCALE`, else the Windows user locale); interface version 5 tells it (`Nx2GameInfo.language`) and the mod takes that; in an older game it reads these settings itself. To override it, write `"language": "fr"` or `"en"` into the mod's `settings.json` by hand (`"auto"` or nothing: the game's); `OOT_COOP_LANG=fr|en` forces it, for tests. The keys of the old language row (`menu_language`, `menu_language_game`) are taken out of the file at the next save.
- **Typing.** A field's row shows its text. **With a keyboard** the name, address and port rows are the game's own text rows (interface version 4's `text_max`): choosing one puts a cursor mark after the text, the keyboard types, Enter confirms, Esc puts the old text back; the mod then takes the text by the field's rule (a refused one is put back and the caption says the rule). **With a gamepad** (a gamepad alone cannot type into the game's row) and for the password rows, the typing is the mod's own: choosing the row starts it (`capture_input`, the game gets no input), up and down change the last character through the field's alphabet, right adds one, left removes one, A confirms, B cancels; a keyboard types into it too. Which of the two a row is follows the player's last press: the interface says whether a press of the game's buttons came from a key or from a gamepad (`Nx2PadEvent.keyboard`), and the rows change hands at the next frame; before any press (a mouse) they are the game's. `OOT_COOP_MENU_TYPING=pad` or `game` holds one way, for tests. The name starts as the Windows user name (else "Link"), the port as 27510. A password is typed anew each time and afterwards shown only as "défini" / "set".
- **What is kept** for the next start: the name, the host's address and the port, in the mod's `settings.json`, the launcher add-on's file and keys. A password typed here is kept under Windows' data protection for this Windows user (`join_password_protected`, `server_password_protected`), never as clear text, and never in `coop.ini`. The session's other options (overlay, puppets, follow, ...) are the launcher add-on's toggles from the same file.
- **Status** on the first page: offline, connecting, hosting or connected with the player number. With a session running, Start and Join say that the game has to be restarted for another one.

**Captions are two lines.** The game's caption box under the list does not wrap, and a longer line is cut at its right edge (seen cut: "Lance le serveur co-op sur ce PC et y joue. Vos amis..."). The runtime passes a line break on since interface version 4's last build, so every caption of the page is at most two lines of at most 46 characters each (`tests/nx2navi_test.cpp` checks every row of every page in both languages, typing or not, every address kind and every sentence the DLL puts there).

**One page, five sets of rows.** The five pages have the same number of rows of the same kinds for the game (eight: five buttons, the ornament line, two buttons; a text row is a button to it, and a list page with fewer saves than rows shows the empty ones as disabled rows), so going from one to another is `update_menu` with other rows: at once, with no trip through the title menu. Opening the next page over the open one (`open_menu` inside the page's event, interface version 4) was tried (`OOT_COOP_MENU_PAGES=replace`, run `k2`): it works, the new page starts with the cursor on its first row, and the title menu shows for 1.25 s in between. The update reads better and is what the mod does; its one flaw is that the cursor stays on the row index it was on (choosing "Héberger en réseau local", the second entry, leaves the cursor on the Host page's second row, "Port"): interface version 5 follows the page's `focus_row` (the cursor glides to the new page's first row, or back to the entry that led there, about half a second later; seen by the runtime's author, `launcher-testt8-menu-sheet.png`); version 4 took the wish and left the cursor.

**The caption after an update.** The game sets the caption under the list when the cursor comes to a row, and the runtime gives the row's text to that call; an update of the open page does not make the game set it again. So what the mod says in the caption of the row under the cursor (the help while typing, a refusal's reason, "Copiée", "Sauvegarde reçue...") would only show once the cursor moved. The mod therefore hooks the game's settings screen's caption function (main+0x34031d0 in game 1.1.1, `(screen, row type)`) to learn the screen and the row it last set, and makes that same call again after each update it sends (`title_menu.cpp`, `RefreshCaption`). It is this build's address, used only when the game says it is 1.1.1, and it belonged in the runtime's `update_menu`: **interface version 5 does it there, and with `api->version >= 5` the mod registers no hook and makes no call of its own** (`OOT_COOP_MENU_CAPTION=own` keeps them, for a comparison).

A game without interface version 3 has no entry (`menu: no Multiplayer entry on the title screen: it needs NX2navi's plugin interface version 3 ...`); the launcher's row works with every build.

### Multiplayer saves: the saves co-op is played on

A session hosted from the title page never plays on the player's own saves. It plays on a **multiplayer save**: a whole save folder of its own, kept in the mod folder, which only co-op uses.

```
<game>\mods\OoT Co-op\coop-saves\Zelda\save\<account>\slot_00\progress.sav, caption.sav
                                               \account.sav, option.sav   (copies of the player's own settings)
                                  \save-tx, \save-backup                  (the runtime's own, as in a profile)
                                 \Quête@Saria\...     a save received from Saria's game (below)
                                 \_deleted\<name>\... what the player deleted, kept once
```

- **Where the game is put on it.** The game opens its save folder once, at its start, and reads its list of saves then. So **Start on the Host page starts the game again** on the chosen save's folder: the interface's `restart` (version 4) with `NX2NAVI_SAVE_DIR=<mod>\coop-saves\<name>`, `OOT_COOP_INI` and `OOT_COOP_MP_HOST=1` (and the join password in `OOT_COOP_PASSWORD`, never in a file). The game that starts then starts the server and the session itself (`host: this game was started again to host on a multiplayer save`), and the player chooses **Continue** as always, or a new game for a save that has nothing in it yet. Only the save folder moves: the cache, the settings of NX2navi and everything else stay the profile's. A game started normally afterwards is on the player's own saves again. Interface version 5's `set_save_dir` (no restart) is **not used**: with it the game keeps the list it read at its start, so its load dialog would show the caption and picture of the player's own newest save while loading another, a player without a save of their own would have no Continue, and a new save could not be begun; the restart has none of that and costs the time of one start.
- **The pages** (`dll/menu_model.cpp`, `dll/title_menu.cpp`; the files are `dll/mp_saves.cpp`). The Host page's **Save** row shows the save chosen and opens the list; the first page's **Multiplayer saves** row opens the same list (its value is how many there are). The list shows three saves at a time, the last played first, each with the date it was last played ("New game" for one not begun) and, in the caption, the place it was saved in (the scene's name, read from the slot's `caption.sav`; the game's own file, of which only that one text is looked for) and whose it is; **More saves** shows the next three. **New save** is a text row: the name typed (1 to 16 characters, none of `\ / : * ? " < > | @`; "Coop", "Coop 2" ... is offered) makes an empty save folder with the player's own `account.sav` and `option.sav` in it: a game to begin. **Copy my solo save** makes one ("Solo", "Solo 2" ...) from the newest slot of the player's own saves: that slot's files and the two settings files are copied (real copies, never hard links; the slot keeps its name), and nothing of the player's own folder is changed. Choosing a save opens its own page: **Play on it** (chooses it and goes to the Host page with the cursor on Start), **Name** (another name; not for a received save), when it was last played, the place, whose it is, and **Delete**.
- **Delete is asked twice**: the first choice turns the button into "Confirm" and the caption into the question; the second deletes; moving the cursor to another row lets go. A deleted save is not destroyed: its folder is moved to `coop-saves\_deleted\<name>` (an earlier one of that name there is replaced), from where it can be put back by hand. The save the game runs on cannot be renamed or deleted.
- **A new save and a friend who joins before its first save.** A host on a save with nothing in it yet has no slot to send. Its game then answers the joiner's ask with "a new game" and the save's name (one `SAVE_PART` transfer whose bytes are `OOTSNEW1` and the name), and the joiner's game restarts on an empty save folder of its own (`<name>@<host>`, with the player's settings and no slot): its title menu has no Continue either, and both begin the game's own new game. Each game then saves its own new game into its own folder; the host's is the reference from the next join on. Without this the joiner would have gone on in its running game, on its own saves (which is still what happens with a host that has no save and is not on a multiplayer save, or when nobody hosts: the page says "load one of your own").
- **Start without a save** is refused with "Choose a multiplayer save first": there is no hosting on the player's own saves from this page. The chosen save is kept for the next start (`"mp_save"` in the mod's `settings.json`).
- **The launcher's Host** gives the game the same folder at its start (`NX2NAVI_SAVE_DIR` in the game's environment: no second start) when a save was chosen on the game's page before; with none chosen yet it says so in its log and the game uses the player's own saves, as before this page existed.
- **A game without interface version 4** (no `restart`) cannot be put on another save folder: the rows say so ("Unavailable", "Your own") and a host plays on its own saves, as until coop-dll 0.7. `OOT_COOP_MP_SAVES=0` gives the same in any game, for a comparison.

**What each player keeps.** The host's multiplayer save is the reference: the host's game writes it (the game's own saves and autosaves), and it is what the next session continues. A joiner's game gets a copy of it when it joins ([below](#the-hosts-save-for-a-joiner)) and keeps that copy among its own multiplayer saves as `<the host's save name>@<the host's player name>` ("Zelda (Saria)" on the pages). During the session the joiner's game saves into its copy what that player did; the next time the joiner joins that save, the copy is replaced by the host's current one (what the joiner had is kept once, in the copy's `save-previous`). So progress made together lives in the host's save, and a joiner who wants to go on without the host can host on their copy (it is a multiplayer save like any other: listed, playable, deletable; it keeps the host's name for it). The player's own solo saves are never written by either side: the code refuses to make a multiplayer save inside the player's own save folder or to copy from a multiplayer save as if it were a solo one, and the tests compare every file of the player's own profile before and after.

### The host's save for a joiner

Only the host picks a save. A joiner's game takes the host's newest save slot **before it loads anything**, over the protocol's `SAVE_ASK` and `SAVE_PART`, as the emulator kit does ([`coop/host/save_transfer.hpp`](../coop/host/include/coop/host/save_transfer.hpp), [`lichii/hook/coop_save.cpp`](../lichii/hook/coop_save.cpp)):

1. **The host** (inside its session, `dll/save_sync.cpp`): a guest's ask is answered once with the newest `slot_NN` (by `progress.sav`'s time) of the game's committed save folder, `game_info()->save_dir` (interface version 2), packed and split by `coop::host::save`, a part a frame. It works from the title screen on (the host has not loaded yet: Continue then loads that same newest slot). A host with no save yet, or on interface version 1, sends nothing.
2. **The joiner, before its session**: a client of its own joins under the player's name, waits for the server to name the host, asks, puts the parts together, checks the CRC and says goodbye (the name is free again at once). No answer at the address in 12 s, a refusal, or no save within 15 s of the ask each end it with their own words.
3. **The co-op save folder** is one of the joiner's [multiplayer saves](#multiplayer-saves-the-saves-co-op-is-played-on): `<mod>\coop-saves\<the host's save name>@<the host's player name>\` (until coop-dll 0.7 it was one folder for every host, `<mod>\coop-save`; that folder is no longer read or written and can be deleted). The slot is written as `slot_00` of `save\<account>\` in it, with copies of the player's own `account.uid`, `account.sav` and `option.sav` (their settings, never the host's). **The player's own saves are never written**: the code refuses a folder that is the game's own profile, holds it, or lies in its save folder. What the folder held from the join before is kept once, in its `save-previous`. **The save's name** comes from the host right after the save, as one more small transfer of the same kind (`SAVE_PART`s whose bytes are `OOTSNAM1` and the name; `dll/save_sync.cpp`): the protocol and the save's own packing are unchanged, and a joiner of an older build has left before it arrives. The joiner waits 1.5 s for it; a host of an older build, or one that is not on a multiplayer save (the launcher's Host with none chosen), tells none and the folder is `@<the host's player name>`. The name is not trusted: only a text that could be typed as a save's name is taken, and every character a folder name cannot hold is replaced.
4. **The restart.** The game opens its save folder once, at its start, and keeps its progress in memory, so a save cannot be swapped under a running game. With interface version 4's last build **the runtime restarts the game itself**: the mod calls `restart(env)` with `NX2NAVI_SAVE_DIR=<that folder>` (only the save moves: the cache and everything else stay the player's profile), `OOT_COOP_INI`, `OOT_COOP_SAVE_READY=1` and the password in `OOT_COOP_PASSWORD`; the runtime ends the game in an orderly way (the exit callbacks run: the session says goodbye) and starts it again with the same command line and those variables. Measured (run `j2`): 2.1 s from choosing Join to the restart being asked (the save came in 0.6 s; 1.5 s are the mod's own pause so "Sauvegarde reçue. Le jeu redémarre" can be read), and 1.4 s from there to the first log line of the new process. A runtime without `restart` (interface version 2 or 3, or `OOT_COOP_RESTART=own`) gets the mod's own way: the game is closed as its window's close button does and, in the exit callback, started again as NX2navi's own Restart does (the same command line, `NX2NAVI_RESTART_WAIT` naming the old process; an older runtime gets the folder as a whole profile, `NX2NAVI_PROFILE_DIR`). The restarted game connects at once; **Continue** loads the host's save, and the join at the host puts the player beside the host.
5. **When it cannot be had** (the host has no save, the joiner is the first on the server, the game has no exit callback or no window to close): the session goes on in the running game with the player's own saves, and the page says which.

The launcher's Join does the same through `host_save = 1` in `coop.ini`: the game starts, the DLL takes the save and the game starts once more on the co-op profile.

**Can the second start be avoided?** Two cases:

- **A join from the title screen's page: not with this runtime.** The game has opened its save storage (`storage_init`, some seconds after the process starts) long before the player reaches the page, and the runtime reads `NX2NAVI_SAVE_DIR` only there. It would need the runtime to move its save storage to another folder while the title screen shows (before any slot is loaded): an interface call such as `set_save_dir(path)`. Asked for in the runtime's notes.
- **The launcher's Join: yes, and it is not built yet.** There the game starts with `OOT_COOP_INI` and `host_save = 1`, and the DLL is in the process before any of the game's code runs (`nx2navi_plugin_init`). It could take the host's save right there and put `NX2NAVI_SAVE_DIR` into the process's own environment before the game opens its storage: one start, no restart. What it needs: the fetch done before the storage opens (so the start waits for it: about a second with a host that answers, the 12 s of the "no answer" wait with one that does not), and the name of the player's account folder before the storage is open (`game_info()->save_dir` is empty until then; the profile's `save\<account>` has to be found from the profile folder). Until that is written, the launcher's Join restarts once like the page's. Not sent: the host's later saves (the progress the host makes after the transfer reaches the joiner's file only through the game's own saves of what both played), and a host who loads an OLDER slot from the load list instead of Continue plays another save than the one that was sent.

### Shared enemies

The emulator hook's own shared enemies and boss rooms, on interface version 2 ([`dll/objects/INTEGRATION.md`](dll/objects/INTEGRATION.md)): one game owns each enemy and the others show a copy that the Mover places where the owner's is, in the owner's animation, with the owner's life. **On by default since coop-dll 0.7** (`objects = 0` turns it off; every player should use the same setting): in two full two-game runs the second player's strikes and kills, the enemies' owners and the townspeople left out all held with no fault, at the frame rate of `objects = 0` ("Verified, and not": runs `v1`, `v2`, `w1`, `w0`). What was not seen in a game is said there too, a boss fight first of all.

**A copy's own AI.** A copy is the game's own enemy, so the copy's game runs its AI too: it chooses its own animations (the Mover then has to put the owner's back), turns to the local Link and attacks it. The emulator hook's answer was the "brain skip" bit of the enemy's BSA component, set or cleared for held copies (`objects_ai_hold = 1` or `2`, [`dll/objects/hold.hpp`](dll/objects/hold.hpp)). Neither stops the AI here: with the bit as asked in every held copy-frame, the copies still chose their own animation in 41% of the Mover's plays (mode 2: 15 of 37), as often as with no hold (28 of 53).

**What stops it** (`objects_ai_hold = 3`, the default with `objects = 1`; [`dll/objects/brain.hpp`](dll/objects/brain.hpp)): the actor's AI update is left out for held copies. Found with function hooks ([`dll/ai_probe.cpp`](dll/ai_probe.cpp), `OOT_COOP_PROBE=as`): a hook on the game's AS play main+0x2022a0 logged, for every animation an `Enemy_` actor asked for by itself, who called (the return address and the return addresses on the stack above it; run `p1`, 45 kinds of calls from Stalchildren, Tektites, Guays, ReDeads, a Poe, a Skulltula, a Business Scrub). Every chain runs through the node trees at main+0x74xxxx (`f_74d7b0`, `f_74d660`, `f_74cf90`, ...), and those are entered from the functions at main+0xbe000 to 0xcf000, of which **main+0xcb9c0 `(actor, times)`** is the one with a single caller: main+0x2c1e33c in **main+0x2c1d740 `(actor, times)`, the actor's calc of a frame**, which runs the actor's components one after the other and calls 0xcb9c0 in the middle (it also holds the one reader of the brain skip bit that the emulator notes name, at main+0xcc014). A `hook_function` on main+0xcb9c0 sets `skip` when its actor's BSA component (`[[actor + 0x270] + 0xb0]`) is in the Mover's hold table (the same table the brain-skip modes use: enemy copies this game does not own that the owner's samples place right now). The rest of the actor's frame runs: the animation the Mover plays is animated and shown, and the Mover's placing holds (off from where it put them: 0.03 units on average, 0.10 at most). An enemy that becomes ours is not in the next table, so its AI runs again from that frame.

**Two things a copy still needs from that update**, found by running it:

- **Taking a hit.** A hit comes into the copy's Life component as a record: the game's own when our Link strikes the copy, the Mover's when the owner's game says the enemy was struck. The Life step (main+0x49d8c0, called from the actor's calc before 0xcb9c0) takes the record in, but the life only goes down, and the enemy only flinches, in the update that is left out: with it always left out no replayed hit was taken (0 of 8; the Mover wrote the life itself after its wait). So the copy's update runs for 8 frames after a hit came in: when the Mover wrote a record into that Life component, or when the id in the attack's header (Life +0x200) changed.
- **Its first second and a half.** An enemy made as a copy and held from its first frame never leaves its first state (a Stalchild is still under the ground to itself, whatever the Mover shows), and the first hit on it was not taken even with the rule above (4 of 8). So a copy's first 45 updates as a held copy run.

**The second player's own strike.** A strike of our Link on a held copy is the game's own hit on its own actor: the hit's id in the copy's Life component changes, the copy's AI update runs for 8 frames, the game takes the life off and plays the flinch or the death, and the hook's walk, which sees a copy's life fall by nothing it wrote itself, sends the fall to the owner as `DAMAGE` 0.1 s later. The owner's game replays it as a hit record on its own enemy, which then loses the same life there, and a kill comes back as the owner's `OBJECT_REMOVE` (dead), on which the copy, already dying by its own game's doing, is taken off the list. Seen in the game: runs `s2`, `v1`, `v2` under "Verified, and not".

**Who an enemy goes for.** An enemy's AI knows one Link, its own game's, so an enemy goes for the player whose game owns it; "the nearest player" is a matter of who owns it:

- **Rolled enemies (the night's Stalchildren) are their roller's.** One game decides a scene's rolls (the first player's) so that two players side by side get one set, not two; with `objects_rolls_apart` (30 m, this port's rule) a player further than that from the first one keeps the Stalchildren its own game rolls around it, owns them and is the one they attack, and the other games show them as copies. Before, such a player had none (run `n1`: 60 s in the field at night without one). A Stalchild whose player leaves sinks into the ground by its own AI and the others' copies go with it.
- **Placed enemies move to the nearer player's game when their owner is clearly farther**: the server's rule, out of a fight (no hit and no chase of the owner's Link for 12 s), for a player within 30 m who is at least 10 m nearer than the owner, with the owner over 40 m away or that player within 20 m, held for 3 s. Measured in the game with two players who swap places four times (run `n2`, a Guay 15 m from one player and 90 m from the other): the Guay was the near player's 12.4 to 16.0 s after each swap (9.1 and 9.5 s in runs `v1` and `v2`), and dived at that player from then on.
- **In a fight it stays.** While an enemy chases its owner's Link or was hit in the last 12 s it does not change hands, however near another player stands: two players in one fight are attacked by the enemies each of them owns. A strike moves an enemy to the striker only when its owner is well away (the server's rule).

**Townspeople and animals are each game's own.** The hook shares every `Npc_` and `Animal_` actor too. Only enemy copies are held from their own AI, and a held actor could not be talked to or mounted at all, so in this port they are not shared (`objects_friendly = 1` shares them as the emulator build does): Malon, Ingo, the horses, the cows and the cuccos are run by each game for its own player, as without the mod.

**A hitch is not a scene change.** The hook forgets what it shares when it is told the player has no scene (a load). A frame in which the player merely could not be read no longer says so ([`dll/objects/scene_gate.hpp`](dll/objects/scene_gate.hpp)): when the game's thread makes no frame for a second, the DLL's own thread keeps the session alive with a frame without a reading, and that frame used to make the host share its enemies again under new ids (run `s1`: two and three copies of each Stalchild in the other game).

**Measured** (two games at 30 frames a second, Hyrule Field at night, Links that walk a few steps so Stalchildren come; the same scripts in every run; "Verified, and not" has the runs): the copy's own AI chose the animation in **193 of 215** of the Mover's plays with no hold (90%; at the 4 frames a second of the earlier runs it was 41 to 54%), in **0 of 19, 0 of 25 and 0 of 27** with the update always left out, and in **8 of 35** in the final form, all eight in the copies' first second and a half; after that the Mover has nothing to put back at all (`0 plays in 5.0 s`, line after line). Replayed hits taken by the game: **8 of 8** in the final form, as with the AI running.

### Shared progress (experimental, off)

With `share_progress = 1` the session shares the player's items (`item_shared_flags()`, [docs/items.md](../docs/items.md)) through `FlagWatcher`, `GameFlagStore` and `ItemFlagStore`, as the hook does without a flag list file. **It writes into the running game's flag queues from a thread the game does not know, and has never run against the real game in this port.** Its writes go through `WriteProcessMemory`, which changes a page's protection for a moment and puts the old one back: next to NX2navi's own page protections (frozen regions, the lazy write-back) that can leave a page with the wrong protection, one more reason it is off. It should be moved onto the game thread (as teleport's writes are) before anyone turns it on. Not shared, because the hook's code for them needs the emulator: dungeon state, story and cutscene flags, chests and one-time pickups, small keys given back, the host's save for a guest. The game is not held while the host's table comes in. Back up the save before turning it on; every player should use the same setting.

## What works

- Host and Join from the launcher, with the kit's rules and messages.
- With interface version 2: shared enemies ([Shared enemies](#shared-enemies)): the same enemies in every player's game, with one place, life and death; a second player's strikes and kills count; an enemy goes for the player whose game runs it and changes hands to the clearly nearer player out of a fight; each player away from the first has Stalchildren of their own.
- With interface version 3: Host and Join from inside the game, on the title screen's "Multiplayer" / "Multijoueur" page in the game's own menu style; a host's server started and stopped by the game. With version 4: typing rows for a keyboard, two-line captions, this PC's home network address first.
- The game's frame rate with the mod: the same as without it (30.0 of 30 in the test's settings; [Frame rate](#frame-rate)).
- A joiner takes the host's save before it loads anything, into a save folder of its own, and the game starts again on it (the player's own saves untouched).
- Joining a session of this repo's server, with or without a join password; reconnects.
- Your position, rotation, scene, age, animation name, equipment and cutscene state sent to the others (`PLAYER_SAMPLE`, `PLAYER_STATUS`, `PLAYER_EQUIP`). A player on the emulator build should see your marker and a puppet that follows them; with `puppet = 1` and the plugin interface your bone-by-bone pose (`PLAYER_POSE`) is sent too. Not yet seen with an emulator player.
- With the plugin interface and the puppet pack: each other player in your scene as a second Link of their age, at their position and facing, in their pose (running seen: arms and legs mid-stride, leaning into the run, turning round), with their sword, shield, tunic and Ocarina on (seen: Master Sword, Hylian Shield, `Armor_Adult_Normal`, `Item_Ocarina_Time` and its holder, all "returned 0x1"); hidden during your own cutscene, held during theirs; deleted when they leave (seen: gone 2 s after the other game ended). Seen with two adult Links in Hyrule Field, both ways.
- The others' joins, leaves, chat, scenes and positions in the log; with the plugin interface also in the in-game panel and notices, and chat both ways from the in-game box (above).
- With the plugin interface: the join at the host, `/teleport`, the follow through an exit and the way back to the host after a Game Over, as far as "Verified, and not" says.
- With interface version 4: each other player's name over their head, in their colour.
- With interface version 2: the other players as dots on the field's minimap, exactly on the game's own transform.

## What does not work, and what it would take

The emulator build gets inside the game in three ways. A stock (older) NX2navi offers a DLL none of them; one with the plugin interface offers a frame callback on the game's thread with guest calls, drawing over the picture and keys, which is what the panel and chat box use. The table says what a stock build lacks and, where it differs, what is still missing with the interface:

1. **Code in the game.** The hook patches two instructions in `main` to branch to a small AArch64 routine in unused space (`coop_svc.s`, `coop_hold.s`), which calls back into the emulator once a frame on the game's own thread. Everything that calls game functions runs there. NX2navi translated `main` to C ahead of time: instructions written into its memory are never executed, and the memory is read-only.
2. **The renderer.** Markers and the camera come from a call the emulator patch adds after each draw.
3. **The emulator's window.** The panel, chat box and player list are Qt windows over the emulator's render window.

| Missing | Why | What NX2navi would have to offer |
|---|---|---|

| Their Navi, their sounds placed right, thrown and shot things | The fairy, the object and the projectile code of the hook (`coop_fairy.cpp`, `coop_objects*.cpp`, `coop_spawn.cpp`, `coop_projectiles.cpp`) are callers of the same cave and use the emulator's memory and logging types. | Nothing more from NX2navi than the row above; they have to be freed of the emulator's types first, as `coop_puppet.cpp` is. |

| Host and Join inside the game | A menu in the game, typed text, a server process, a save swapped before the game opens it. | Done with interface version 3 (`add_title_button`, `open_menu`, `on_pad`), and with version 4 its typing rows for a keyboard, two-line captions and pages without filler rows. | Shared objects, drops, projectiles, time of day | The same. | Nothing more from NX2navi than version 2; not ported. |
| Holding the game while a flag snapshot comes in | The hook pauses the frame step. | A pause call (version 2's hook can skip a function, but skipping the frame step does not freeze the world: the runtime's notes). |
| The host's save for a guest | The save transfer writes the emulator's save folder. | Done with interface version 2 (`save_dir`, `on_exit`) and a restart of the game on the save folder the host's slot was written to, since version 4 by the runtime's own `restart` ([The host's save for a joiner](#the-hosts-save-for-a-joiner)). | A goodbye when the game closes | The DLL's threads are ended with the process. | Done with version 2's `on_exit` (an orderly end; a killed game still leaves by the server's timeout). |

NX2navi has its own co-op layer (its `docs/coop.md`). It is another system with another protocol; this mod does not talk to it, and the two should not be used in one game.
