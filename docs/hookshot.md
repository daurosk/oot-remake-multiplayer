# Squadala! on Longshot (formerly Hookshot; Stage 2: recomp)

[Longshot](https://git.magicbean.dev/MagicBeanDev/Longshot) (Team MagicBean and contributors, GPL-3.0; https://longshot.magicbean.dev/) is a static recompilation by Team MagicBean whose changes are being merged into [Hookshot](https://git.notrexed.dev/Hookshot/Hookshot) (NotRexed and contributors, self-hosted): a static recompilation of the same game build co-op already supports, main build id `e0f3ccfaf50065ae` (version 1.1.1). It is the version co-op builds on until something better is out. The game's AArch64 code is translated to C ahead of time from the player's own dump, compiled for x86-64 Windows and Linux, with Horizon OS and NVN2 written natively and the GPU work replayed on Vulkan. No CPU or GPU emulation.

Co-op runs on it as Stage 2 (see [plan.md](plan.md)), and every release since 0.10.1 runs on it (the release kits have no emulator). This page is the design, for Longshot commit `e4d035e9e71a8375964052195727ff87b1845047` (v3.0.0-rc.5, released 2026-11-16; before it v3.0.0-rc.4 `53f96d780588`, v3.0.0-rc.3 `0c74253d4c6e`, v3.0.0-rc.2 `e7ed2f7a6526` and Hookshot `4aee23659b94`, v2.2.0-rc.1); the files are in `hookshot/` ([hookshot/README.md](../hookshot/README.md)); what is proven is under Status. Below, "Hookshot" means the same code base under either name.

## Short answer

- Co-op fits Hookshot better than the emulator. The emulator cannot call a game function, so `lichii/hook` writes caves into main and talks to them through a custom SVC. Hookshot calls a game function from host C directly (`a64_lookup(address)(ctx)`), and adds C after any ordinary instruction at build time (`Lifter.after`; not after a call). The SVC cave, the hold cave and their assembly go away.
- Hookshot already does, for its own menu, much of what we need: a hook on Link's update (`hos_oot_is_player`), game function calls by address (`oot_teleport`, the GameDataMgr getters), the current map, cross-map teleports, and a local control socket for tests.
- Addresses: Hookshot loads main at **`0x80020000`** (Eden's layout: rtld at `0x80000000`, then main). Every offset in `CoopGameBuild::MainOffsets` becomes `0x80020000 + offset`. Checked on one function: our `set_time` `0x34522d0` is Hookshot's `0x834722d0` (`hos_main.c` `oot_set_time`). Data slots go through the same offsets; the first runs check them. In our patches a game function is a constant written as main + offset (`0x80020000ULL + 0x33e4200ULL`), never a bare `0x8...` literal in `guest_call`/`a64_lookup` (`tests/hookshot/module_test.cpp` checks every patch): patch 0018's HUD refresh was `0x833e4200`, the offset put on `0x80000000`, the middle of another function, so its lookup failed and the refresh (rows 63/76) never ran up to 0.11.4. It now looks the function up first, counts `hud_refreshes` only when it ran and logs once (`menu: the HUD refresh ... is not in this build of the game`) when it is missing.
- Emulator and Hookshot players can join the same game: same game build, same coordinates and data, same protocol, same server. Nothing on the wire says which runs the game. (A Hookshot game shows the others as Link with our Hookshot patch 0002; see Status.)
- One copy of co-op for both: the module builds every `lichii/hook` file unchanged, with stand-ins for the emulator API they use (`hookshot/compat`). Our patches to Hookshot are small: the co-op bridge (`hookshot/patches/0001-coop-bridge.patch`) and the puppet guard (`0002-coop-puppets.patch`).

### Where the co-op module lives

Two parts:

1. **Our patch to Hookshot** (`hookshot/patches/0001-coop-bridge.patch`, for the commit in `hookshot/PIN`):
   - `nx2/coop_hooks.py`: the frame hook and the hold hook, each checked against the build id and the instruction words, else left out with a log line. Called from the lift (`nx2/lift.py`, two lines) next to `oot_jitter.install` (rc.4 and rc.5 have no `oot_occlusion`).
   - `host/coop_bridge.c`: on the first frame hook, loads `hookshot_coop.dll` from beside the exe (unless `HOS_COOP=0`) and hands it the C table in `host/hos_coop_api.h`: main's base and build id, the game folder, read, write, a 32-bit compare-and-swap, call (`a64_lookup` with the game's `Ctx` saved and put back whole, arguments in x0-x7, four stack words, s0) and the log. Without the DLL, both hooks return at once.
   - `host/nn_hid.c` (two lines): keeps player 1's buttons word as `GetNpadStates` gives it to the game (`hos_coop_pad`); the table's `pad_buttons` reads it, so your own Ocarina notes are sent as from the emulator's pad (issue 152). A module on a Hookshot built from an older patch still starts, without notes (its start line says so).
   - `host/nvn_native.c` (two lines): `nvnQueuePresentTexture` calls the bridge's `hos_coop_present`, which calls the module with `HOS_COOP_SITE_PRESENT` once it is loaded. The module runs `CoopHook::OnFrame` there, once per present, loads and pause included, as the emulator runs it at the guest's present; the callers' game calls stay at the every-frame site (they need the game's context). On a Hookshot from an older patch (no present calls) OnFrame stays at the every-frame site.
   - `gpu/vk/vk_coop.cpp`, `vk_coop.h`, `hos_coop_draw.h` and three lines in `vk_menu.cpp`: when the module (found by name once loaded) has chat lines or name tags to show, the menu's ImGui frame is made and they are drawn under the menu. A module with `hos_coop_draw2` gets the whole table: the HUD pack's fonts (ImGui `AddFontFromFileTTF`, any time with ImGui 1.92) and pictures (`ImTextureData` + `RegisterUserTexture`, copied in on the present's command buffer as the logo) are loaded once and kept.
   - `host/display.c` (two cases) and `host/nn_hid.c` (one line): key presses and characters go to the module first (`hos_coop_key`, `hos_coop_char`); while `hos_coop_keys_taken` says so, the game reads no keys, as while Hookshot's own menu is open. Also the mouse: `display.c` offers the cursor (a fraction of the client area: `hos_coop_mouse`) on a move, a left click and the wheel while no menu has the mouse, and lets a captured mouse go when a key opened the chat box or the panel.
   - `nx2/build.py` compiles every `host/*.c` and `gpu/vk/*.cpp` already. Its Linux link exports, each by name, the exe's functions the module finds with `dlsym(RTLD_DEFAULT, ...)`: `hos_coop_fs_save_root` and `hos_coop_fs_save_remount` (patch 0008), `hos_coop_fs_save_slot_opened` (0025), `hos_coop_input_select` and `hos_coop_input_pad_name` (0015), `hos_coop_pad_info`, `hos_coop_pad_read` and `hos_coop_pad_take` (0016), `hos_coop_textures` and `hos_coop_texture_override` (0020, the module's live look) and `hos_coop_texture_overridden` and `hos_coop_texture_overlay` (0020, which the exe's own renderers find by name). Hookshot's link exports only `hos_posix_*`, so without them the module found none of these on Linux. Not a `hos_coop_*` pattern: the module has functions of the same names as the exe's (`hos_coop_frame`, `hos_coop_key` ...), which an exported exe copy would replace. On Windows they are `dllexport`.
2. **The co-op module** (`hookshot_coop.dll`, CMake target `hookshot_coop`, built with MSVC as the emulator's hook is): **all of `lichii/hook`**, the files `lichii/hook/core.cmake` lists, except the emulator's cave (`coop_svc.cpp`); `coop_testinput.cpp` is built without its pad input and plays the autotest driver's test commands (place, give, assign, chat, setflag, setenum, wear, kill) from the file `LICHII_COOP_TEST_COMMANDS` names. `hookshot/compat/` stands in for the slice of the emulator's API those files use (`Core::System`'s memory, process and build id, the loader's module list, `Common::FS` folders, `LOG_*`), answered from the bridge's table. So every co-op feature of a release is in both builds from one copy of the code, and a hook file that reaches for more of the emulator fails the module's CI build. `hookshot/src/coop_hookshot.cpp` drives it: `CoopHook::Start`, `CoopHook::OnFrame` at the every-frame site, then the callers' game calls (`lichii/hook/coop_callers.{h,cpp}`, the same stepper the emulator's `svc #0xf4` handler asks), the AI hold (from a table in the module's own memory, `CoopHold::HostTable`, which the Objects step publishes; the emulator's hold cave reads the guest table), `CoopHook::Shutdown` at exit.

3. **Actor events** (patch `0007-coop-actor-events.patch`, after 0005's world hook layer; native-plan rows 7-10): `nx2/coop_actor_lift.py` puts C after one instruction in four game functions and hands each call to the module through `host/coop_world.c` (`hos_coop_world`; the numbers are in `hookshot/src/hos_coop_actors.h`): the create request `requestCreateActorAsync` (main+0x372a94: caller, create argument, name, handle slot), the delete request where it is accepted (main+0xa65d0, once for an actor: actor, reason; the Sync then counts the actor gone at the first walk without it, not the second) and the Life component's step (main+0x49dcb0: component and this frame's damage sum, which the module may change: another player's hit goes in through the game's own step, `CoopActorEvents::LifeTable`). The create hook also asks the module whether to stop the request (`HOS_COOP_WORLD_CREATE_STOP`): a copy enemy's own shot (`CoopEnemyShots::StopAtCreate`, the same rule as the walk's: the nearest maker belongs to another player) leaves through the game's own "the manager takes no creates now" exit, so it is never made here and only the owner's shot is seen, as a copy (`LICHII_COOP_ENEMY_SHOTS_STOP=0` turns that off; the walk then deletes it as on the emulator). What the game asks inside one of the module's own calls (a copy made, a remove) is marked as ours and never stopped. Words and build id are checked; the fourth is the game's shoot code (main+0xc16d24, `HOS_COOP_WORLD_SHOOT_FROM`: the shooter's actor, so a copy enemy's shot is known by who fires it and not by where it appears); the build log says `co-op actors: 5 of 5 actor event hooks`. The fifth is the same Life step again, where it is about to test the component's life stops (main+0x49dcbc, `HOS_COOP_WORLD_LIFE_STOPS`): the module may have that frame's sum go past them (a copy taking its owner's death; see docs/dungeons-boss.md, "The life stops"). The module pushes them into a lock-free ring in its own memory (`lichii/hook/coop_actor_events.h`) and the Objects step drains it on the frame hook. A hit of this game's on another game's enemy is taken from that step (`Sync::GameHit`), not from the life read falling: the fall is only paired with it (either may be seen first), a fall while the owner's hurt is in flight is that hurt, and a fall that no step explains within 0.3 s still counts and is logged (`coop: actors: N life fell on copies with no Life step for it`). On Hookshot the module never writes the game's damage field (the step would report it back as a hit): a life change goes through the step, or is written when the step does not take it in 0.25 s (the step skips its sum on two paths: bits 3 and 12 of Life+0x1d18 set, or no life value at Life+0x1c10; the log names the actor: `its Life step did not take the change`). The table of given hits is emptied on every new scene.

A DLL keeps the patch to Hookshot small (it changes only when Hookshot moves) and keeps our C++20 out of Hookshot's C build.

### Hosting from the game (in progress)

A player hosts without the separate server window: the module runs the co-op server on a thread of its own. `server/host_service.hpp` (`HostService`) is coop_server's hosting loop as an object: the game server and, when the host asked, the router forward (UPnP), the relay and the invite code with its answer codes. `coop_server` itself is a loop around the same object, so a dedicated host keeps the standalone server and its window says the same lines. Every session has a join password (a new random one when the host gives none) and encrypted traffic; the router forward opens only when the host said yes. Status for the menu (`HostService::status`): the port, the players, the invite code or why there is none, the last problem in plain English. The Multiplayer tab (below) calls it.

## Texture overrides (patch 0020)

A module may have Longshot's renderer draw a texture with other texels while the game's memory keeps the game's own: `hookshot/patches/0020-coop-texture-override.patch`, header `host/hos_coop_texture.h` (the same file in `hookshot/src`, checked by `module_test.cpp`). The Link customizer paints your own Link's tunic and gear with it ([puppet.md](puppet.md#the-link-customizer)); nothing of the game is written for a look.

- **What the game made.** `nvn_native.c` tells `host/coop_texture.c` each texture at `nvnTextureInitialize` (its storage's guest address, size, width, height, levels, NVN format, and a serial new each time) and at `nvnTextureFinalize`. The exe's export `hos_coop_textures(size_min, size_max, out, max, &generation)` lists them by storage size; the generation changes whenever one is made or finalized, so a module looks again only then.
- **An override.** `hos_coop_texture_override(address, serial, bytes, n)` (an exe export, found by name) copies the bytes; from then on the renderer reads them in place of guest memory `[address, address + n)`, which must lie inside the storage of the texture of that serial while the game has it (a texture made again over the same storage has another serial, so a late call is refused); `bytes` NULL takes that texture's overrides there away. Another texture over the same storage (an alias) shows an override while it lasts. Unit-tested: `tests/hookshot/texture_override_test.cpp` builds `hookshot/src/coop_texture.c`, the patch's file. Setting or taking one away marks its pages written (the soft write watch, `hos_mark_written`: bookkeeping, no write), so the renderer uploads the texture again. A texture finalized (or made again) takes its overrides with it: the memory may hold something else next.
- **The renderer.** Vulkan (`gpu/vk/vk_texture.cpp`, the only one since Longshot rc.5): `guest_bytes`, which every CPU and ASTC upload path reads a texture's storage through, lays the overrides over a copy (`hos_coop_texture_overlay`, found in the exe by name); a texture with an override skips the GPU unswizzle and the all-zero clear, so it is read there too. Without an override nothing changes: one atomic count is read.
- **Generic.** Any module, any texture, no further Longshot build: a candidate for the Longshot add-on API of the 1.0 plan ([plan.md](plan.md)). Linux: the module and the renderers find the exports with `dlsym`, so patch 0001's Linux link exports all four by name (checked by `tests/hookshot/module_test.cpp`).
- **Not proven in a game yet** (2026-11-14, the owner was playing: no game build): that every upload path of our textures (BC1, BC3, ASTC) goes through `guest_bytes`, and that marking the pages makes the Vulkan renderer upload the texture again.

## World hooks

Co-op takes part in the game's world through the game's own functions instead of caves and guest memory. One layer does it, our patch 0005 (`hookshot/patches/0005-coop-world-hooks.patch`, header `hookshot/src/hos_coop_world.h`, Hookshot's `host/coop_world.c`), made when Hookshot is built:

- **Events after one instruction** (`Lifter.after`): `hos_coop_world_event(event, a, b)` reaches the module's optional export `hos_coop_world`. The AI pause counter start (main+`0x5e6778`, `nx2/coop_platform_lift.py`) is `HOS_COOP_WORLD_COUNTER_START`: the node goes into a ring in the module's own memory (`CoopCounters::HostRing`), which the Objects walk reads as it read the guest ring. No game malloc, nothing at main+`0x3c46780`. The emulator keeps its cave.
- **AI node starts** (patch `0029-coop-node-starts.patch`, issue 147; header `hookshot/src/hos_coop_nodes.h`, the same file as the patch's `host/hos_coop_nodes.h`, checked by `module_test.cpp`): one generic event, `HOS_COOP_WORLD_NODE_START` (16, the first of the world's next numbers): a = a started AI node, b = its actor. `nx2/coop_node_lift.py` has one row per hooked start, so another node's start is another row, not another event. First row: the push node of every pushed block (main+`0x2751790`, `ExecuteMovableBoxControl`'s Enter and the Enter of two node classes built on it), after main+`0x27517c0` where it has read the actor. The module keeps the newest node of each actor (`CoopWorld::TheNodeStarts()`, lock-free, in its own memory), and a block another player moved runs its own push node's start again from there ([world.md](world.md), "Blocks: the push node"), with no search of the game's heap. The patch adds no file of 0005's (its number lives in its own header) and could become a module/API call for 1.0 (a mod asking "tell me when this node class starts"), so the game patch would go. An exe without it: no event, the node is "not found", as before.
- **Wrapped game functions** (`Lifter.wraps`, in `third_party/a64-kit/lift/a64_lift.py`, and sent to the emit workers through `nx2/chunks.py`'s `EMIT_TABLES`): every call of a listed function, and the indirect table, reach `hos_coop_w_<entry>` in `a64_hooks.c`, which calls the module's optional export `hos_coop_wrap(id, phase, x, ctx)` before (phase 0; 1 = the module did the call's work) and after (phase 1) the game's own unchanged `f_<entry>`. `nx2/coop_world_wraps.py` lists them with their first words; build id and words are checked, and a function Hookshot hooks or edits by name is never wrapped. First wrap: the flag applier (main+`0xb99980`, `HOS_COOP_WRAP_FLAG_APPLY`), which only counts for now (`coop: world wraps: the game's flag applier ran N times`).

Hookshot keeps the exports only once the module answers `HOS_COOP_WORLD_HELLO` with 1, so a module the bridge refused is never called. The hello carries the hook level (`HOS_COOP_WORLD_VERSION`) and the wraps that build has, a bit for each id; the module logs both, and says so when Hookshot was built with an older patch. Only a function the lift really made is wrapped (not a PLT stub, not one that calls setjmp); the lift prints what it left out. Flags are on this layer: the applier's wrap gives the flag watcher the game's own writes as events, and co-op's writes go through the game's setters on its calc thread ([flags.md](flags.md), "Through the game's own functions"). Time of day is too: the wrap of the game's one time function (main+0xeee640) makes the game's own set the jump the others take ([time.md](time.md), "Through the game's own function"). So are event starts: the wrap of the game's event request (main+0xd7a820) names the event our game started at the request, for a dungeon room's events and the story cutscenes; the search of the event session stays as the emulator's way. With the wrap, a name the search finds is sent only when our game's request named it in this scene since the last save load; any other is a name left in the event session by an earlier load and is logged, not sent (`coop: dungeon:` / `coop: cutscene: an event start found by the search that no request of our game named in this scene: a leftover, not sent`). A function Hookshot's own edits change at its head can be wrapped (the wrap leaves the function's text alone); one whose calls those edits look for by name cannot.

Teleport to another scene has the game's own way behind a switch, `LICHII_COOP_TELEPORT_EVENT=1` (off until a run has shown it): the event `Dm_SY_BancChangeGo` with the arguments `NextBanc`, `NextStartPos`, `BootEventName` (`Dm_SY_BancChangeArrive`) and `IsCheckAir`, started by our Link, as an entrance asks it (the layout of an event's arguments is in `lichii/hook/coop_live_events.h`; Hookshot's own teleport asks the same event). The event calls the game's `ReserveBancChange` and the map loads when it ends, so nothing of co-op is written into the request flags (today: two String64 flags written straight into their buffers, then a plain event to make the game take them). To check in a run with the switch on: `/teleport <player>` to a player in another scene logs `coop: teleport: asking the game's map change event Dm_SY_BancChangeGo for <scene> at <start>`, the map changes once, and Link stands at the other player. Not known yet: whether an entrance's own arrival event (a few scenes have one, such as `Dm_SY_BancChangeArrive_KakarikoVillage_01`) is needed there.

Like the title's rows, which are built on it (`title_menu.py`), it works on the player's own game files at pack time; nothing of the game goes into the repository. The format notes are in the module.

- **A copy of a part**: `clone_part(layout, source, name, move=(x, y), params=...)` adds a copy of one of a layout's parts (a `.buil` of `UI/Layout2Archive`) as the last pane and the last part: new pane and part records, the new name, the grown pane and part dictionaries and the copy's own parameter and properties lists, all after the string pool. No existing offset or index moves (the part records, and it seems the animations, name panes by index). `clone_parts` makes several at once; `edit_entries` edits every copy of a layout in its archive (Title and Common hold each four times). A part that overrides panes of its part layout (its record's lists at +0x08 and +0x18; 70 of the game's 386 parts) is refused for now.
- **Moving panes, and another parent**: `move_panes(layout, {name: (x, y)})` moves panes (their translate, nothing else). A copy can go under another pane than its source's parent (`Copy(..., parent=name)`) when that pane's subtree reaches the layout's last pane, so the pane order holds; its translate is then in that pane's frame, and `frame_offset(layout, pane, ancestor)` gives the move that keeps it where it was (the translates of the panes between them added up; refused when one of them is scaled or turned).
- **Text**: `add_labels(msbt, {label: text})` adds labels and texts to a message file (`LayoutMsg/*.msbt` in each `Mals/<language>` archive); the file's own labels keep their indices and texts. A text pane's own label is its path through the parts, joined by `-` (`PlusMenu_00.msbt` has `Pa_System_00-Pa_Button_00-T_Btn_00`), so a label for a copy's pane names the copy. Labels are letters, digits, `_` and `-`.
- **Our words**: one file per language in `tools/puppet_pack/strings/`: `en.txt`, then `fr.txt`, `de.txt` and so on, or the game's code for one region (`USfr.txt`, `CNzh.txt`). A `[LayoutMsg/<file>.msbt]` line, then `label = text` lines, the labels in the style of that file's own. `load_strings("USfr")` reads `en.txt`, then `fr.txt`, then `USfr.txt` over it; a label a translation leaves out keeps its English text. Only our own words go in these files.

## The save list

Player report 124: after the save folder is switched (a guest gets the host's save, Resync from host, a new session back on the player's own folder) the title showed no Continue, or the old saves, until a restart. The title does not look at the disk: its `SeqQueryIsExistSave` (OpenTitle, NormalTitle, ConfirmationLoad) reads the game's caption manager (`*(*GOT main+0x4c81660)`: +0x8c its state, 0 cleared, 1-3 reading, 4 read; +0x8e a save exists; +0x8f a Master Quest save exists; +0x88 the latest slot; slot tables at +0x8 and +0x48, an entry's +4 its slot, +0x280 bit 0 its file found). The game fills it with `SeqOneshotRequestLoadAndSerializeCaption` (body main+0xf6da00, which calls main+0xf6da40 with the manager), at boot (BeforeInitializeCommon) and on the way back to the title (FormalSequence), followed by `SeqExecuteWaitCaptionMgrStable`.

So every switch goes through one place, `CoopSave`'s `RemountLocked` (the only call of the exe's `hos_coop_fs_save_remount`). It marks the list stale, and the title's step (`coop_title.cpp`, `RefreshSaveList`; logic in `CoopTitleMenu::SaveListRefresh`) has the game do it in its own order: its idle test (main+0x33ad380; state 4 counts as idle once every slot entry is read), its list reset (main+0xbafd40, the callback it registers for that; back to state 0, refused while a save screen holds the list), then that read, which starts only from state 0 (at state 4 the read alone only marks itself wanted). Done when the game's test says idle again with state 4. The module writes nothing in the list. The log says `coop: title: save list: ...` with the bytes before and after. No new patch: the title hook's `call()` (patch 0004) already runs game functions.

The module keeps these as main offsets (the ones named above) and makes guest addresses only through `CoopRuntime::MainBase()` (main is mapped at 0x80020000; `coop_title.cpp` `Main()`, as the rest of the module does). They were first written as guest addresses, 0x80000000 + the offset, 0x20000 short (a code word read as the GOT, calls into the middle of other functions), which is why the save-refresh run saw "the title step never asked"; `tests/hookshot/module_test.cpp` checks each against the offsets named here and that no guest address is written in the file.

## The host's save as it is now (a guest's ask)

A guest's ask while the host plays a file is answered with a save written after the ask (docs/flags.md, "The save sent is the host's game now", case 1). The host's game is asked for its own autosave with the call the game's `EventTriggerRequestAutoSave` event node makes at the end of an event (its body main+0x31f2f50, read from main): the AutoSaveMgr is the game system's component 0xc (main+0xba7880(system, 0xc), the system from the GOT at main+0x4c7e178), then main+0xba7730(mgr, 5, 0), kind 5 being that node's. That function runs the game's own gate (main+0xba72d0: refused while the manager is off or busy, while the game's autosave-off flag is set, in its cooldown right after a save, or in a player state it does not save in) and otherwise only marks the request in the manager's state (+0x130); the manager saves at its own next step into the slot it always uses. `coop_hookshot.cpp` `RequestHostAutoSave` makes the call on the calc thread's call site, once a round (`CoopSave::TakeSaveRequest`), and writes nothing in the game. Log: `coop: save: asked our game for its own autosave ...`, then `coop: save: our game saved after the ask ...` or, after 6 s, `coop: save: our game did not save within 6 s of the ask ...: sending our last save on disk`.

## Risks

- **Memory.** A Hookshot game takes about 10 GB of RAM; 8 GB of VRAM is recommended. Two games on one PC are fine on the test PC (128 GB of RAM) at the normal preset; players with 16 to 32 GB of RAM should run one game each.
- **Open crashes and GPU limits.** Hookshot needs Vulkan 1.3 with mesh shaders (RTX 20 or newer, RX 6000 or newer); Intel is mostly untested. Open issues there: an intermittent device loss after the first gameplay frames (its design.md, S4), crashes outside Kokiri Forest (Hookshot issues 317, 648), AMD crashes (708, 614).
- **Patch upkeep.** Hookshot moves fast. Our patch touches three new files and two lines of `nx2/lift.py`; moving `hookshot/PIN` (and the kit's list of builder parts with it) is a test like moving the Fritchii pin.
  - **The move to v2.2.0-rc.1** (from c544828, 66 commits). Every hunk of the three patches applied unchanged except one: `host/hos_sdl.c` merged by hand, because Hookshot added its own optional SDL functions on the lines beside our `StartTextInput`. The upstream changes to the files we touch were these: `vk_menu.cpp`'s `menu_record` gained the frame-generation menu, with the same three conditions; `nn_hid.c` gained the stick's dead-zone pairs and `player_used`; `nvn_native.c` and `nx2/build.py` changed only by moving lines. `nx2/lift.py`, `display.c`, `display_sdl.c` and the hook sites did not change. Hookshot's lift now writes the C in several processes on Windows too (its #2748). Our hooks still reach every process, because all three (`coop_hooks.py`, `coop_puppet_guard.py`, `coop_platform_lift.py`) write only `Lifter.after`, which is one of the tables sent to each process (`EMIT_TABLES` in `nx2/chunks.py`). Hookshot's new game patches (the new-game opening, its own zstd) are in other functions.
- **Frame timing.** Hookshot runs at its own speed (30 to 60 fps, a high-fps option). The co-op sampler and puppets work from time, not frames; to check with a puppet in view.
- **Addresses.** Code offsets are checked (`set_time`); the data slots are read through the same `CoopGameBuild` offsets from main's base, and the first runs check them (the scene and Link read, puppets made).
- **The co-op window.** The emulator's Qt window is not on Hookshot; the chat, name tags, player list, panel, HUD and cheats are drawn in Hookshot's ImGui frame instead ("Where the co-op module lives" above).
- **Licences.** Hookshot is GPL-3.0, as we are. Its lifted C contains the game and is never shared; we ship our module, our patch and our scripts, and each player builds Hookshot from their own game.
