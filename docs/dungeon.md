# Dungeons the same for every player

Status: the tables are read from the game's files; the sharing is tested on fake games (`tests/lichii/dungeon_test.cpp`); none of it is played through in a dungeon yet (issue 87).

Plan stage 5: "if someone triggers something in the Water Temple, all players see it happen". Switches, doors, torches, room clears and water levels. Breakables and movable blocks are [world sync](objects.md)'s; enemies are [objects.md](objects.md).

Game: main of build e0f3ccfaf50065ae (1.1.1), romfs of the same version. **Checked** means read from the game's files. **Live** means seen in the running game.

## Results

- **The dungeon's state is in named flags the room logic writes and reads.** A placement is linked to others only by `Reference` links and `EventRequestActor`s (checked, Water Temple). ## What is shared, kind by kind

Every kind of dungeon state, where the game keeps it and whether co-op shares it. "Named" = a named Bool or Int flag of the list above; "key" = a 64-bit placement key ([flags.md](flags.md)); "item" = [items.md](items.md).

| Dungeon state | Where the game keeps it | Shared | How |
|---|---|---|---|
| Switches pressed (floor, eye, crystal), shutters and barred doors opened | Named, written by the room logic (`…_Switch_…`, `…_OpenDoor…`, `…_ShutterOpen`) | Yes | Live, last write wins (host's answer) |
| Torches lit for good (puzzles that stay solved) | Named (`DodongoCavern_CandleStick`, …); the Well's `Obj_Well_CandleStick_A_03` is a key | Yes | Named live; key as one-time |
| Torches that burn out, timed switches | In the actor, or flags of reset type 280 | No | Room-local, back on a reload; each player solves their own |
| Order puzzles (the Scrub Brothers 2-3-1) | The order in the manager actor's own code; the solve in named flags | **The hits, new**, and the solve | A brother hit in one game is given to every other game's manager the game's own way, so players can split the order (below) |
| Room cleared (its enemies beaten, the shutters open) | Named `…_Clear`/`…_Cleared`, and the rooms' `Obj_EnemyCounter_*` keys (51) | Yes | Named live; keys one-time |
| Enemies, pots, grass, ice pillars | Keys of reset type 88 or 280: back on a scene load | No | [objects.md](objects.md) syncs the ones on screen |
| Mini-bosses and bosses beaten | Named (`…_Boss_Defeat`, `…_BossBattleEnd`…) and the heart container's key | Yes | Named live; key one-time |
| Chests opened (small key, map, compass, boss key, items) | Key of the chest's placement, reset type 24 (140 dungeon chests) | **Yes, new** | One-time key: opened in one game, opened in all; never closes again |
| Silver rupees and their counters | Keys (`Obj_RupeeToken_Silver` 85, `Obj_silverRupeeCounter_*` 17) | **Yes, new** | One-time keys |
| Walls and floors blown or hammered open, webs burnt, red ice melted, ghost paintings, skull pots, falling floors | Keys of reset type 24 (`WallCrack`, `*_CrackWall_*`, `*_SpiderWeb_*`, `Obj_RedIce_*`, `Obj_FireTemple_HammerSlipPillar_*` …) | **Yes, new** | One-time keys |
| Outside the dungeons (row 220): boulders blown up or thrown away, cracked walls, grotto covers, the Hyrule Field grottos' webs, Zora's Domain's red ice, a grotto's or the Graveyard's enemies beaten | Keys of reset type 24 (`Obj_BrokenRock_*` 60, `Obj_LiftRock_B` 46, `WallCrack` 15, `*_HidingHoleCover_A` 17, 12 webs, 2 red ice, 5 enemy counters, 1 crack wall: 158, `CoopDungeon::WorldKeys`) | **Yes, new** | One-time keys. Before, each stayed done only in the game that did it, and in that player's game too only until it loaded the host's save. Left out: Boss Rush (`DreamWorld`) and the minigames' targets |
| Gold Skulltulas in dungeons, heart containers, the few hearts and rupees of type 24 | Keys | **Yes** (also as pickups, [items.md](items.md)) | One-time keys |
| Water level (Water Temple) and other dungeon Ints | Named Int (`WaterTemple_Room00_WaterLevel`) | Yes | Live, last write wins |
| Map, compass, boss key owned | Item: `DungeonInfo.<dungeon>.IsGetMap` / `IsGetCompass` / `IsGetBossKey` | Yes | OR: once anyone has it, everyone has it |
| Floors shown on the map | Item: `DungeonInfo.<dungeon>.EnteredFloorBit` (UInt, a bit a floor; the map's get sets them all) | Yes | Bits: the union of every player's floors (below) |
| Small keys in the pocket | Item: `DungeonInfo.<dungeon>.SmallKeyNum` (Int) | Yes | **One shared count per dungeon** (below) |
| Locked doors unlocked | Named (`…_UnLock`, `…_OpenDoor…`) | Yes | Live |
| Business scrubs sold out, fairy fountains (reset type 25) | Keys | No | Not known what type 25 means; left out |
| Where each player is, Navi's hints, the camera, "in battle" | Named, reset types 1, 9, 32, 40, or one-player names | No | Each player's own |

### Small keys: one shared count

`SmallKeyNum` is a count, not a flag, and uses the count (delta) rule of [items.md](items.md): every change a player makes (+1 for a key picked up, −1 for a door opened) is added to the one count all players have for that dungeon. So the players share one key ring. A key cannot be had twice: its chest is a one-time key (above), so once one player has opened it, it is open in every game and the +1 is counted once. Keys that drop from an event write named flags that are shared (`FireTemple_GetSmallKey_01` to `_08`, `BottomOfTheWell_Level_Room_03_Get_SmallKey`). The only two loose `Obj_Dungeon_SmallKey` placements (Bottom of the Well and Shadow Temple, `*_Static`) have no key of their own; the Well's has the named flag just given, the Shadow Temple's is not mapped and could be taken twice (check in a run). A door opened by one player costs one key for everyone, and the door's flag opens it in the other games, so nobody pays for it twice.

### The map and compass stay got (issue 146, minimap-b)

**The map's floors (map-get-b, 2026-11-14).** In the owner's playtest the opener (game B, the host) got the Deku Tree map and saw it on neither the minimap nor the Map page. Co-op had written no flag in B (`flags native: ... 0 setter calls made for co-op`), no `coop: map-drop:` line came, and B's own saves made around the get keep `IsGetMap` at 1. Comparing B's autosave before the get with the one after it shows what the get writes: `IsGetMap` 0 -> 1, the chest's opened Bool `0xe4fb555d`, four item help-box Bools (structs 0x2b05cbb9, 0x41f3e410, 0x541947d0, 0x57f52eb8), and **`DungeonInfo.InsideTheDekuTree.EnteredFloorBit` (UInt 0x5c6c21c1) 12 -> 31**, every floor. Only `IsGetMap` was shared, so another player's map stayed at the floors that player had entered. `EnteredFloorBit` of all 14 dungeons is now a shared item (`ItemRule::bits`, the union, sent and set through the game's UInt setter 0x57af30; GameFlagStore reads and writes a UInt only for such an item). Not seen in a game yet; if the opener's own map is still missing with both values set, the cause is elsewhere (the big run's check names both games).

**The root cause (dungeon-maps-a, rows 63/76, 2026-11-16).** The Map page and the minimap do not read these flags live. The HUD screen keeps its own copy (floors, and the map, compass and boss key) and reads it in only at its init (a scene load) and its refresh, which the game runs after its own get scene, on the Map page and at a room load. The game's rebuild fills every floor when the dungeon's `IsGetMap` is set. So the getter's map shows at once (its get scene ends in a refresh), and a map already in the save shows on entering. But a value co-op writes during play (another player's item, the join snapshot, a reset, a put-back, the solo keeper) skips the refresh: the minimap stayed blank until the Map page or a room load (run `hs-map-opener` 2026-11-16, `LICHII_COOP_MAP_PROBE=1` logs the copy). The fix (`lichii/hook/coop_map_refresh.h`, on unless `LICHII_COOP_MAP_REFRESH=0`) asks the game's own refresh once after any such write of a map, compass, boss key or floors, in every dungeon, in a session and alone, while Link is in play; Longshot patch 0018 runs it at the HUD screen's own next update (never on a stored screen pointer). A guest's floors also survive the host's reset and its own load write-back (an exact write ORs the floors).

The log and the guard below came first, while the cause was not found.

The game's minimap and the Map page read `DungeonInfo.<dungeon>.IsGetMap` again only when the Map page opens or a room loads (a research run, 2026-11-14: the flag set while Link stood still left the minimap dark until the Map page was opened). So a map lost earlier shows up exactly as players reported: "the map is gone from the minimap after I opened the Map page" or "after a new room". What takes the flag back was not seen in three research runs (the Map page, the pause menu, floors, a walk and a new load of the room all kept it, with the module and without).

- **The log** (`coop::host::MapDropLog`, `coop/host/map_drop_log.hpp`; in a session and alone): whenever any dungeon's map or compass goes from 1 to 0, wherever Link is (also on the title screen), one warning line `coop: map-drop: DungeonInfo.<dungeon>.IsGetMap 1 -> 0 [(outside its dungeon <dungeon>)] in <scene> at x y z, in play|loading, game menu open|closed|unknown, Map page shown|not shown|unknown; our code wrote it: no|YES (<what>, -N s); last 10 s: [...]`. A drop seen while the game is not in play (a load, the title) waits up to 3 s: the game clears its whole flag table before it loads a save and when it goes back to the title, a moment before it says so, and that is no drop in play. When the game says within those 3 s that it starts loading a save, loaded one or shows the title, the line is an information line that ends `; N s later: <what>: the game's own clear of its flags, no drop in play`; when nothing says so, it is the warning, ending `; no save load and no title followed in 3 s` (player report 269: 13 such warnings in one session, each right before a save load, hid the real ones). A drop in play is a warning at once. The last 10 s list the Map page and game menus opening and closing (Hookshot with patch 0018; without it "unknown"), loads (a room or scene change), scene changes, save loads, sessions starting and ending, the flag watcher's join snapshot and save-load resets, and every write of ours to a map or compass flag with what made it (the flag watcher, its join snapshot, the host's save-load reset, its one-way restore, the solo keeper, co-op code). At most three such lines a flag, then one summary a minute (`... went 1 -> 0 N more times since the last line`); more than three flags at once (a save load) make one line naming them all. A player's log with that line says what happened just before.
- **The guard, in a session**: the flag watcher writes a dropped map or compass back (`ItemFlagStore::is_one_way`). Only against a value seen in play in the same save: a save load, also the host's through the title menu, starts again from the new save ([flags.md](flags.md), "A load window"). A player's 0.11.2 host log (Forest Temple, player reports 106-108) showed the old rule: the host's mid-session load through the title was not seen as a save load, so the old save's floors (`EnteredFloorBit`) were written into the new save, and the game wrote its own back once a frame, about 4,000 writes.
- **The guard, alone** (`coop::host::OneWayKeeper`, `coop/host/one_way_keeper.hpp`, run from the hook's frame while co-op is off): only a map or compass the game itself gave while it watched (seen going 0 to 1 in play, no session), in this save, written back to 1 through the game's own Bool setter if it goes to 0 while Link is in that dungeon (or across a room load there). Its baseline is dropped at every save load (no scene for 1.5 s: the title screen, the file list) and whenever a session starts or ends, so a map from one save or session is never written into another. Log: `coop: items: DungeonInfo.<dungeon>.IsGetMap went back to 0 with no session: written back (minimap-b guard; ...)`. `LICHII_COOP_KEEP_MAPS=0` turns it off (the log stays).

The other cause of a missing minimap is not this: the game's `MapIconDeactivateByAreaActor` (0x9a4dd779) hides it while Link touches a `UI_MapIconArea` area, which is placed only in the overworld (Death Mountain Trail and Crater, Desert Colossus, Zora's Fountain, Hyrule Castle, Ganon's Castle), never in a dungeon.

### Later players

A player who joins later gets the host's table of every shared flag and key (`FLAG_SNAPSHOT`, [protocol.md](protocol.md)): doors open, chests open, rooms cleared, keys and dungeon items as the group has them. One exception from the one-time rule: a key a late joiner's own save has at 1 while the host's is 0 stays 1 in the joiner's game but is not sent to the host (the watcher's first read is its baseline); it reaches the others only when it changes again.

## The Deku Tree slingshot room (issue 129)

A player test (2026-11-10): in the slingshot room the trap was not shared, and the ladder did not fall in the other game although the pillar moved; a player who had not opened the chest could not leave. Read from the romfs (no run):

- The room is `InsideTheDekuTree` room index 2 (`DefaultDungeonRoomIndex`, the slingshot chest `Obj_TBox_A_02`, key `0x0b66198d17d6584e`, at -54.4 112.0 12.2). Its logic graph is `Logic/InsideTheDekuTree_Level_Room_C_Prefab_efa7`: the eye switch `Obj_EyeSwitch_A_02` (hit with the slingshot), an `EventRequestActor` for `InsideTheDekuTree_Gimmick_FallingLadder`, the pillar `Obj_InsideTheDekuTree_Stopper_A_01`, the ladder `Obj_InsideTheDekuTree_FallingLadder_A_01`, both chests, a boot-up node, `TriggerGameDataSetBoolTrue` on `InsideTheDekuTree_RoomC_Cleared` and `TriggerDungeonRoomStep…`.
- **The trap** is the falling floor by the chest (`Obj_InsideTheDekuTree_FallingFloor_A_01`, `_A_02`, `_A_03`; `_A_02` links a `FallingFloorBreakPos` anchor 3 m below). `_A_01` and `_A_02` are saved placement keys (`0xe9f286aa47fef9b1`, `0x61f7b4da35494840`); that build did not share them, the dungeon placement keys (above) do.
- **The pillar and the ladder** have no flag of their own. Both are on/off animation actors (`OnOffAnimController`, the ladder `OffToOnOnly`) driven by a bool of the room graph (`QueryLogicGetBool`). In that build `InsideTheDekuTree_RoomC_Cleared` was already shared, `HavePlayedEvent.InsideTheDekuTree_Gimmick_FallingLadder` was not. That fits what was seen: the pillar follows the room's flag, the ladder follows the event, which only A's game played.
- **The fix here:** the played gimmick events above are shared, so B's game has the same record that the ladder event played. What is not known without a run: whether B's room, already loaded, puts the ladder down at once or only when it loads again (item 1 below). If only on a reload, the next step is to play the event in B (the game's event request by name), which needs a new message.

## Order puzzles (issue 149)

A player test (2026-11-11), Deku Tree, the three Scrub Brothers to hit in the order 2, 3, 1: B hit 2, A hit 3, B hit 1 and the puzzle did not solve; A alone doing the whole order solved it. Read from the romfs (no run):

- **Where the order is kept.** The brothers are three `Enemy_Scrub_Deku_Brothers` (Banc `InsideTheDekuTree_Static`, room index 9, names `Two` `ShootOrder 2`, `Three` `ShootOrder 3 DefeatedOrder 2`, `One` `DefeatedOrder 3`) linked to a `Scrub_Deku_Brothers_Manager`. A hit (`AI/Scrub_Deku_Brothers.action.interruptsmallhit.module`) sends the scrub's `DefeatedOrder` to the manager (`OneShotSendScrubDekuBrothersDefeatedOrderMessage`); the manager's AI is one native node (`ExecuteScrubDekuManagerAI`) with no flag for the count. So the progress is in each game's manager actor, fed only by hits in that game. A stun changes no life, so no `DAMAGE` ([objects.md](objects.md)) ever carries one player's hit into another game.
- **The solve.** The last scrub's `DamageEventName` `Talk_Deku_03_Attacked` is an entry of `Event/EventFlow/Get_StoneOfForest`, the one place besides the room graphs that names `InsideTheDekuTree_Dungeon_EnemyScrubDekuDestroy_003` and `InsideTheDekuTree_RoomK_Cleared`. The room graph (`Logic/InsideTheDekuTree_Level_Room_K_Prefab_6708`) only reads those two (`HoldGameDataGetBoolSimple`), and the boss-door shutter's graph (`…_Room_K_Prefab_52bd`, `DungeonSwitchShutterWithLockSet`) reads `RoomK_Cleared`. Both flags were already shared, so one player's solve opens the room in every game.
- **A failed try.** The room graph sets `InsideTheDekuTree_RoomK_Failure` (`TriggerGameDataSetBoolTrue`); nothing in the romfs reads it. It was shared; now it is not, so one player's wrong order can never reach another game in the middle of that player's own try.
- **The other two scrub flags stay shared.** `InsideTheDekuTree_Dungeon_EnemyScrubDekuDestroy_001` and `_002` are not steps of the brothers' try: they belong to the two lone `Enemy_Scrub_Deku` (room index 1, `DamageEventName` `Talk_Deku_01_Attacked`; room index 5, `Talk_Deku_02_Attacked`). Each is set once, when that one scrub is beaten: `_001` by its talk in `Get_StoneOfForest` (room B's graph only reads it), `_002` by room F's graph (`TriggerGameDataSetBoolTrue`). The brothers' utility graph and `Navi_EnemyHint_Normal_1` only read `_002`. Shared, a scrub beaten in one game is beaten in all, as the room clears are.
- **The brothers are each game's own** (`CoopObjects::IsOwnPuzzle`). They were shared as enemy copies: the owner's animation was played over a non-owner's own hit reaction (`Sleep`, `GetUpBrothers`), which could spoil a solo try by the player who did not own them. Now each game runs its own three.

**dungeon-switches (player test 2026-11-11, still per player):** the brothers and their manager are now in the gimmick probe (`LICHII_COOP_GIMMICK_PROBE=1`), so one run in their room logs which words a hit steps in the scrub and in the manager. With those, a hit can be sent and the count written in the other games (message types 216-220 are kept for it). Writing a hit record into a scrub was never taken by the game ([objects.md](objects.md), "Life on copies"), so there is no replay of the stun yet.

**deku-scrubs (issue 149): the hits are shared.** Read from main (`lichii/hook/coop_scrubs.h` has the addresses):

- **How a hit reaches the manager.** The brother's node `OneShotSendScrubDekuBrothersDefeatedOrderMessage` (execute main+0x292e810) calls the game's message send main+0x2838c50 with: the sender, the brother's transceiver (actor + 0x3e0; its id, a u32, at + 0x3e8); a header of the manager's transceiver id (manager actor + 0x3e8), the message `0x77440000` and a 0 byte; and a 0x18-byte payload whose first u32 is the brother's `DefeatedOrder` (Two 1, the blackboard's default; Three 2; One 3). ### Held until the room loads (issue 129, player report)

A player test: in the Deku Tree slingshot room A shot the eye switch and A's ladder fell. B's ladder did not fall, B's eye stayed open, and shooting B's own eye then did nothing: a softlock. B's ladder was down after B reloaded the save. So the shared flags were right, but B's loaded room did not play the result, and the played-event flag stopped B's own switch from playing it. The game has no known way, from the hook, to start that event in B, and the scene change that would reload the room is taken only while an event runs. So the rule is the other half: **never mark a gimmick done in a game without its result**.

- Every `HavePlayedEvent.<gimmick>` flag of the list whose result hangs on our room's asker (class asker, about 47 of the 202; the others are class live, see "Result only" below) and the Forest Temple corridor's state flags (`ForestTemple_TwistCorridor_IsReverse`, `…01/02_IsConstraint`, `ForestTemple_SageOfForest_TwistedCorridor_A_01` to `_04`) are held while our Link is in that flag's dungeon (`CoopDungeon::HeldIn`; a gimmick event of no one dungeon is held in any dungeon).
- Held means our game does not take it yet (`coop::host::HoldFlagStore`). The watcher keeps the value and writes it as soon as our Link is out of that dungeon, or the game is loading (no Link: a save load, a scene change), so the room loads with it. A host answers a held write with the value asked, so the group keeps it.
- Meanwhile our own switch still works: shooting B's eye plays B's own ladder event. Its flag then goes out as B's change, and the held value is dropped (the game set it itself).
- The room's own flags (`…_RoomC_Cleared`, switches, doors, the water level Int, small keys) stay live. The pillar in the slingshot room followed them live in the 2026-11-10 player test.
- The log says `coop: dungeon: room gimmick flags from another player held until we leave this dungeon or load` and `no room gimmick flags held`.
- The corridor (docs/sync-coverage.md): its state is shared, but never applied under a player who is in the Forest Temple; it is applied on their next load or entry.
- **Not held** (row 98(2)): an event of class live (every room result by a shared flag the room graph reads live; `CoopEventResult::IsLive`, generated from the room graphs). The Deku Tree basement water (`…_Gimmick_RoomG_WaterLevelDrop`) and the torch room (`…_Gimmick_RoomH_CandleStick`), which came live in a player test, are two of them; the hand-made list they were on is gone.
- **A load never undoes a held value for the group.** A held flag written while there was no Link (the join snapshot, a save load), which the save then loads over with 0 while our Link is in the dungeon, is kept to write later. Its 0 is ours alone and is never sent (review of 08fad87).
- **Released only after a real load**: about 0.5 s (30 frames) without our Link, not one frame the reader missed. The scene is the last one read.
- **The way out** when a gimmick's own trigger is itself a live-shared saved flag (B's switch already counts as pressed, so B cannot play the event): leave the dungeon (or reload) and come back. The room then loads with the event played. The live events (below) start the event in B's game instead, once B's Link comes near it.

## Locked doors (branch `locked-doors`)

A small-key door is a door set (`Logic/Module/DungeonDoorSingleWithChainLockSet`, `DungeonSwitchShutter…WithChainLockSet`, placed as `AiGroups`) with a lock actor, `Obj_DoorChainLock_*` (98 placements: Fire 16, Gerudo Training Ground 18, Forest 11, Shadow 10, Spirit 10, Water 9, Well 4, Gerudo Fortress cells 4, Ganon's Castle 3, the rest in the Dream World). The lock's AI (`AI/DoorChainLock.root.ainb`) spends the key (`OneShotDungeonUseSmallKey`), saves "open" in a bool it makes from its placement (`QueryGetIsGenerateAutogenGameDataFromGameBancParam`, `OneShotSetGameDataBool`) and deletes itself (`OneShotDeathRequestDeath`). That bool is no placement key and no name we could hash, so it is not in the shared list; only some rooms also write a named flag (Forest `…_LockOpne`, Spirit `…_Unlocked*`, Ice Cavern, the Well).

With the key count shared and the lock not, the second player found the door still locked with the key already spent for both: one key short per door, a softlock in every dungeon with locked doors. Now the lock itself is shared, as a world object (`CoopWorld::WorldSync`, [world.md](world.md)):

- **0.11.2 (dungeon-sync-b, player report #75: "keys are shared and removed when used, but the door unlocked only for the player who opened it"): the lock is kept and a key is lent again, by default.** Read from the door set's graph (`Logic/DungeonDoorSingleWithChainLockSet_de9c`, `…Large_f25d`): the door (`ActorLogicDungeonDoor`) takes `OpenKey <- OR(ANDPulse(lock A.ReceiveDoAttention), ANDPulse(lock B.ReceiveDoAttention))`, a pulse that comes only when a player uses a key on a lock. A lock that leaves another way (our delete, 0.11.0's default) sends no pulse, so the door stayed shut in every game but the opener's. So a lock another player opened is no longer deleted (`LICHII_COOP_LOCK_DELETE=1` deletes it, as in 0.11.0); our player opens it the game's own way with the key lent below. The lent key no longer reaches the group (that was why lending was off): `coop::host::LentKeys` (`coop/host/lent_keys.hpp`) writes the +1 into our game only and shows the flag watcher the count without it (`LentKeyStore`, between the item store and the watcher). Our game's own drop of that count while a key is lent spends the lent key first (the lock), and the watcher sees nothing; a key found meanwhile is the group's as usual; a group total or another player's change written in keeps the lent key on top; a take-back (-1) is unseen too. The spend goes to the world sync as our drop, so `lock opened here with the lent key` still settles it. A save load forgets lent keys. Log lines: `coop: doors: small key 0x… lent to our game only (N -> N+1; the group's count stays N)`, `coop: doors: lent small key 0x… taken back (…)`. Not run in a game yet: the check is the big run's (reports/dungeon-sync-b.md). A lent key not used goes back once our Link is 3 m from its lock (was 6 m): off that door, so it can never open a different lock.

- **Opened here:** our lock leaves the actor list next to our Link (the game deleted it) and goes out as `WORLD_BREAK` with the `kept` bit (protocol 7).
- **The server keeps it** for the session, also while nobody is in the dungeon, and gives it to everyone who enters, a late joiner too. Other breaks are forgotten when a scene empties, since the game puts pots back on a reload; the opener's game never puts a lock back.
- **Opened elsewhere (only with `LICHII_COOP_LOCK_DELETE=1` since `door-unlock`, see below):** our copy of that lock is deleted (0.4 s after the break, or at once when its room loads later), so our door is open and no key of ours is spent. A lock deleted that way that comes back when its room loads again is deleted again, never reported as put back.
- **Status (2026-11-12, two-game run on the emulator, scenario `lock-own-key`'s first form): keeping the lock with a lent key is OFF by default again.** In the run the lent +1 went to the other players as a found key (their log: `A found a Small Key (Water Temple) - the group has 2`), and the non-opener still had its own key, so after one door both games held 2 keys from a start of 1. A player left at a shut door types `/teleport <name>`: inside a dungeon it now moves to any room (seen twice in that run).

Players reach a door together, so the second player stood within the 2.5 m in which the lock is left alone, and the opener had spent the group's key: no key, a shut lock. And no run has ever shown that a door opens when we delete its lock (the `lock-open` runs of 2026-11-12 show the opener's break sent and the other game's two locks deleted, but the second player's walk through the door failed for a reason of the test script); a deleted lock on a door that stays shut could not be opened at all. Our player opens the lock as the game does (the same prompt and key as the first player, which the run shows working); that spend is the lent key, so nothing more goes back and the group has paid one key for the door. One lent key at a time (a door's two locks get one), at most 8 per lock and visit of the dungeon; a lent key not used goes back (-1) when our Link is 6 m from the lock (3 m since dungeon-sync-b), when the lock or its room leaves without a key of ours spent, or when we leave the dungeon.
