# Boss rooms together

Issue 109. Caleb: "if two players are in the same dungeon and one walks into boss room, both players should receive the same cutscene and fight it together."

Game: main of build e0f3ccfaf50065ae (1.1.1), romfs of the same version. **Checked** means read from the game's files. **Live** means seen in the running game. Nothing on this page has been seen live yet.

Code: `lichii/hook/coop_boss.{h,cpp}` (the rooms and the rules, no emulator code; tests in `tests/lichii/boss_test.cpp`), `lichii/hook/coop_boss_game.cpp` (reads the game, moves Link, skips the intro). Message: `BOSS_ROOM`, type 50 ([protocol.md](protocol.md)).

## What the game files say

- **A boss room is a room of its dungeon's scene, not a scene of its own** (checked). `Banc/<Dungeon>/` holds one Static and one Dynamic file per dungeon; the boss, its heart container and its blue warp (`Obj_WarpPoint_A_01`) are placements in it with `Dynamic.DefaultDungeonRoomIndex` set to the boss room. So "walking into the boss room" changes no scene, and the scene name alone cannot tell it. The hook tests where Link stands instead: the dungeon's scene and a circle and height band around the room's placements.
- **The boss rush has a start point for every fight** (checked). `Banc/DreamWorld` (the boss rush) has a `StartPos` named `<Boss>Stage` for each boss, at the same coordinates as that boss's room in its dungeon (for example `GohmaStage` at 6.7 47.0 67.6, the Deku Tree's `StartPos_Get_StoneOfForest`). A moved player is put there.
- `GameBancParam` also has `DodongoStage`, `PhantomGanonStage`, `GanonStage`, `GanondorfStage` and `BossRushIntervalRoom`; those are the boss rush's, not the dungeons'.

## How it works

1. **Entering.** A game whose Link is in a boss room sends `BOSS_ROOM` at once and every 2 s while there, saying how far it is: "in the room" while only near (the room's circle also takes in the way to the door), "intro started" during its intro (it is past the door, which shut behind it), and "intro over" in the fight.
   - **Only past the door moves anyone (issue 148).** A player test in the Deku Tree: A came near the boss room; B was moved in, the door shut in B's game, and A, not yet through the corridor to the cutscene that shuts it, was locked out. Now only a player whose intro has started, or who is fighting, moves the others in; "in the room" alone never does. A room entered without any intro for 10 s counts as a fight in that game, but moves no one in: no event says that player is past the door. A game that joins late learns from the heartbeat whether a fight is on.
   - **Past the door is the game's own word (issue 148, second report).** An event near the room is not always the intro: the door opening, a text box or Navi on the way are events too, and the room's circle takes in the way. So "intro started" is sent only once the player is past the door:
     - Deku Tree: the game's own `InsideTheDekuTree_BossArea_ShutIn` (the flag that shut the door when it was shared) is read every frame in that scene (`CoopBoss::ShutInFlag`, `Local::shut_in`). Set while Link is in the room: past the door, at once, also with no intro (seen before). An event that ends while it is still 0 was not the intro: the wait starts again (log `that event was not the intro (not shut in the room): nobody is moved in`).
     - The other rooms (no such flag known): an intro that lasted at least 3 s (`kMinIntroUs`) and ended with Link still in the room sends "intro over"; a shorter event is not the intro. So the others are moved in at the end of the leader's intro, and their own intro is skipped to follow.
     - A player our own pull put in the room a moment ago is past the door.
     - A fight that began here with no intro while nobody is past the door (no event for 10 s, or only events that were not the intro) takes its next event as a possible intro, judged the same way, not as the boss's death (unless the boss is already seen dead). Otherwise a real intro coming more than 10 s after a door event would have pulled nobody, and a 15 s one would have counted as the boss beaten.
     - Not measured: the 3 s rule outside the Deku Tree. A door or boss-key event of 3 s or more that ends with Link inside the room's circle would still move the others in early there.
     - Log: `past the door (shut in)`, `past the door (the intro is over)` or `past the door (moved in)`, then the others move in. `LICHII_COOP_DEBUG_BOSS=1` adds `shut in 0/1/-` to the phase line.
     - Autotest `gohma-movein` (A in Gohma's room, B at the entrance).
   - **No shared "shut in" (issue 148).** In the same run, after the lock-out both players loaded saves, and both were then locked out. `InsideTheDekuTree_BossArea_ShutIn` (with `ChangeENVForBoss`) was a shared dungeon flag, so the join snapshot gave every reloaded game the shut boss door. These flags say where one player is in a fight, not what the group did, so they are no longer shared: `CoopDungeon::NotShared()` (also `ShadowTemple_Level_StartBossBattle` and `InsideGanonCastle_IsEnterBossRoom`). The boss beaten, its heart container and a boss door unlocked with the key stay shared. The server keeps flags only while it runs, so a group stuck on an old build gets out by restarting the server. Dodongo's and the Fire Temple's `BossGroundChange` (the arena's floor as the fight starts) are left out the same way. A save that already holds one of these at 1 (written while an older build shared them) is mended: once per scene load, while Link is in no boss room, the hook sets them back to 0 in that game (`CoopBoss::StaleBossFlags`, log `coop: boss: <flag> was left set in this save ...: cleared`).
2. **Moving the others in.** A game whose Link is in the same dungeon scene, but not in that room, moves Link to the room's arrival point, 1.5 units from it by player number. It tries again every 3 s while the other player is still fighting there, at most 5 times per fight. This is also rule 4: a player who joins or dies during the fight comes back in the dungeon's scene (the game restarts a dead Link at the dungeon's entrance) and is moved in again. The pull stops when nobody has said "in the room" for 6 s, when they left, or when the boss is beaten.
   - **How Link is moved.** While an event runs in our own game, the game's own scene change takes a request (as the autotest `warp`, [testing.md](testing.md)): `Sequence_ReservedNextStartPosName` = the room's StartPos, then `Sequence_ReservedNextBanc` = the dungeon; the dungeon loads again with Link in the boss room. In free play the scene change is not taken (seen in autotest runs), so the hook does what the AI node `ExecuteActorForceSetMtx` does: writes Link's place (actor +0x31c) and calls the actor's vtable slot 0x218 = 0x4c6580(actor, 0), the engine's warp of the whole physics body ([world.md](world.md)). The scene stays loaded. `LICHII_COOP_BOSS_MOVE=matrix` always uses this one. The Spirit Temple's room has no StartPos, so it is always moved this way.
3. **The intro.** An event in the first 10 s of the fight (`kMinFightUs`) is never the boss's death. In integrate-p8, a game that skipped its intro took the next event, 0.1 s later, for the outro and sent `defeated` with nobody fighting. The first event that starts while Link is in the room is the intro (`intro started`); its end is `intro over`. A game cannot start another game's intro: a moved player's own game plays it when Link arrives (if the room starts it on entry; check 4). To leave together, a game whose intro still runs once any other player in that room has finished theirs skips the rest of it with the game's own force skip: `SeqOneShotEventRequestForceSkip` (0x32d1890) takes the event manager, and while an event runs calls 0x3b3af30 with the current event (`[[S+0xeb8] + 8 * u32 [S+0xf18]]`, `S` = manager +0x68). The hook does the same from the svc cave, every 0.5 s for up to 6 s. If no event starts within 10 s of entering (the intro was seen before), the fight has begun.
4. **The boss's death.** The next event in the room after the fight began may be the outro. Not every event is: in the integrate-p7 run (Water Temple), an event of about 6 s during the fight (Morpha's tentacle grabbing Link, most likely) was taken for the death. That game sent `defeated`, every game stopped its fight, and a player who then walked out was not pulled back. So when the object walk (`LICHII_COOP_OBJECTS=1`, the kit default) can read the boss, the event is only the death once the boss's body actors (`CoopBoss::Bodies`: the boss actor; for Twinrova also Koume and Kotake; never eggs, minions or shots) are gone or at 0 life (`CoopObjects::LastBossAlive`), or once it has run 15 s. A body actor whose life is not read makes the reading unknown, and then the old rule holds (only Morpha's life is seen read so far). Taking the room's own outro event by name would be surer, but the hook reads only the running event's address, not its name. An event that ends with the boss alive goes back to the fight (`the event is over and the boss is alive: the fight goes on`), and the heartbeat goes on while it is decided. Without that reading, the first event is the death, as before. After a real death nobody is pulled into that room again until they leave the dungeon's scene: walking out of a beaten boss room is allowed, by design (the heart container and blue warp are there, and there is nothing left to fight).

Off with `LICHII_COOP_BOSS=0`. `LICHII_COOP_DEBUG_BOSS=1` logs the phase each second. Log lines start `coop: boss:`. The cave (moves and skips) is patched in only with puppets or spawns on (`LICHII_COOP_PUPPET`, as every kit has).

## The boss goes to the player who hurts it (issue 150)

A player test (Gohma): the boss only ever followed and attacked player 1, its owner; and after player 2 stunned it, player 2's copy was turned the wrong way and could not be hit until player 1 hit it.

**Why.** Only the owner's game runs the boss; every other game's copy is held to the owner's pose and animation. A boss is in its fight for 60 s after every hit (`boss_fight_lock_us`), and an object in a fight never changes owner, so the boss stayed with player 1 for the whole fight. Its AI in player 1's game only knows player 1's Link (the game has one player; the puppets are not targets), so it went for player 1 alone. Player 2's seed in the eye stunned player 2's copy in player 2's game (the weak point hit and chance time are in Gohma's own AI: `DungeonBossGohma.action.interruptweakpointhit`, `.interruptchancetime`), but not player 1's boss; the copy then kept being turned to player 1's boss while its own AI lay stunned, until player 1's own hit changed the owner's state.

**What changed (server, `Session::on_damage`).** A `DAMAGE` on a boss or any part of its group from a player who does not own it hands the boss root (and so the group) to that player, at most once every 8 s (`boss_hitter_cooldown_us`; 0 turns it off). The hit's effect, a stun included, is then in the owner's game, the other copies follow it, and the boss turns on the player who hurt it last: in a long fight it goes back and forth with the hits, which gives both players their turns. It is not handed over while its owner hits it too: a life drop in the owner's samples with no `DAMAGE` passed on in the second before is the owner's own hit, and for 6 s after one (`boss_owner_hit_hold_us`) the boss stays, so two players hitting in turn do not bounce it (each hand-over can jump a phase: the state carries only place, turn, animation and life). The distance rule for plain enemies is unchanged. Tested in `tests/server/session_test.cpp` (issue 150 cases).

**Stuns (hook).** A stun that takes no life showed no hit. Now a boss copy whose own game starts a stun animation the owner's boss is not playing (first word `Stun`, `Down`, `Fall` or `Faint`: Gohma's `Stun_St_Attack_Chance`, `Stun_Lp`, `Down_Start`, `Fall_St`, read from its `AS` file) sends a `DAMAGE` of 0, at most every 2 s, and keeps its own stun on screen like a hit reaction (the owner's animation from before waits 0.7 s). The server takes it like any boss hit: the boss goes to the stunner, whose own boss is the stunned one. The owner's game ignores an amount of 0. Tested in `tests/lichii/objects_test.cpp` (issue 150 cases).

**The near player (server, `Session::run_ownership`).** The owner's AI only knows the owner's Link. Off by default since gohma-sync (`boss_near_hold_us` 0; the fight keeps one owner, below). Turned on (`boss_near_hold_us` 4000000), a boss in its fight also moves to a fit player within 15 m of it and 4 m nearer than its owner for that long in a row (`boss_near_m`, `boss_near_margin_m`), not while its owner hits it and not within 8 s of the last change. So when player 1 stands back, the boss turns on player 2. Making the owner's AI target the other player's puppet was looked at and left alone: the game's target choice reads its one player actor.

**After a hand-over (on by default since branch `enemy-sync`, not proven).** The new owner's boss was a copy whose own AI phase may differ from the pose it was held to (on the floor while the pose was on the ceiling): it froze or walked in the air. The AI state (AINB) is not known, so it is not copied. An enemy that becomes ours gets bit 23 of actor +0x4a8 (set by the Mover's setter every frame, docs/world.md) cleared once, in case the game leaves it set and holds the body. This is not only a boss question: Hyrule Field moves the owner of the Peahat and other enemies often (chase, wake and distance rules), and a Peahat that never woke for either player (issue 157) fits the same frozen body, so the clear is on for every enemy that comes to us from another owner. `LICHII_COOP_OBJECTS_RELEASE=0` turns it off. The 5 s log line `release: N that became ours had bit 23 set (cleared), M had it clear, K skipped (over 64 in a frame)` says how often the bit was really left set: if N stays 0 in a run with hand-overs, the bit is not the cause.

## One owner for the fight, the eye guard copied (branch gohma-sync, issue 150)

A player test (2026-11-12): "Ghoma can enter stun state but have its eye guarded for one player while its eye is not guarded for another, this means only one player can attack it. Ghomas animations and height are all over the place."

**Why.** Two things together.
- *Only slot 0 was copied.* Gohma's `AS` file (`AS/Enemy_DungeonBoss_Gohma.root.asb`) has more than the body: `GuardArm`, `GuardDefault`, `GuardWait`, `Eyelids`, `Eyelid_Up`, `Eyelid_Down`, and its `AsNode` events (`AnimationEvent/AsNode/Enemy_DungeonBoss_Gohma.root.baev`) include `DisableGuard`, `OverrideReaction` and `WriteBlackboardInt__ASSystem`: the eye's guard is opened and closed by what the animation plays, on slots of its own. The Mover held a copy's slot 0 to the owner's and left every other slot to the copy's own AI. So the stun pose came over, but each game's eye guard was its own.
- *Every hand-over jumped a phase.* The hitter rule (any hit from a non-owner) and the near rule moved the boss several times a fight. Each time the new owner's AI took over from a copy whose phase had never matched (on the floor while the pose was on the ceiling, guarded while the owner's was open): the boss snapped up or down and changed what it was doing. That is the "height all over the place".

**Now.**
- *Hook.* The owner's walk reads a boss's AS slots after slot 0 (`IsBoss`; up to 8; slot array entries 0x48 apart, docs/puppet.md) and sends them as the `slots` component of its samples (19, [protocol.md](protocol.md)); a change of any slot's name sends a sample at once. A copy's Mover plays each named slot on the same slot (the play request's slot index) and sets its frame, as for slot 0, every game frame, so the copy's own AI cannot keep its own guard. Only slot 0 counts as the copy's AI taking over (wake rule, issue 157). A slot the owner plays nothing on is left alone. Log: `copy <address> plays '<name>' at frame F on slot N`.
- *Server.* A boss stays with one owner for the fight: a `DAMAGE` that takes life is passed to the owner, whose game takes it off its boss (the hit replay, as for any copy), and no longer hands the boss over (`boss_hit_handover`, false). Only a stun with no life lost (a `DAMAGE` of 0: a seed in the eye of a copy, whose stun the owner's game cannot have) hands it to the stunner, at most every 8 s, so the stunned boss is the owner's. The near rule is off by default (`boss_near_hold_us` 0). The boss therefore turns on its owner's Link more than on the other player's; that is the price of one consistent boss.
- Tested: `tests/protocol/codec_test.cpp` (the slots component), `tests/lichii/objects_test.cpp` (slots sent, a slot change sends at once, slot wishes for the copy, none for plain enemies), `tests/server/session_test.cpp` (gohma-sync case; the old cases run with the old switches).
- **Not proven** (no game run on this branch): that the copy's guard really follows its slots (if `DisableGuard` is an AI-side flag instead, the eye stays each game's own; then the next step is the AI hold for bosses, docs/objects.md), how many slots Gohma has, and the height after the one stun hand-over. Autotest `gohma-sync` (boss rush room `GohmaStage`, since no kit save is from before Gohma).

## Not known yet (for the in-game check)

1. Whether the force-set-matrix move into a room of the same scene loads that room's walls and floor, or Link falls through (the dungeon may stream rooms by `DungeonRoomIndex`). If he falls, the fallback is the scene change, which needs an event running.
2. Whether the room circles match the walls.
3. Whether the force skip of a boss intro leaves the boss in its fight state (the graphs use it for going back to the title).
4. Whether a moved player's game starts the intro itself, and whether the outro is the first event after the fight (an event in the fight is now checked against the boss's life, step 4; whether the remake removes or zeroes a dead boss actor is not checked).
5. Whether a boss door's own event (the boss key, the door opening) counts as the intro: it starts before Link is inside the circle, so it should not.
